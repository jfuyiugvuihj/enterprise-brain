## 2. 产品当前定位

当前项目是一个私有化部署的企业 AI 智能分析平台，目标场景包括：

- 企业制度、流程、手册等文档问答；
- Excel、CSV 等经营数据分析；
- 图表生成和报告导出；
- 异常指标监控和通知；
- 轻量知识图谱；
- 审批预审建议；
- 多 Agent 协作处理复杂问题。

当前系统的实际形态不是单一的“知识库问答系统”，而是多个能力模块的组合：

```text
用户登录
  -> 文档知识库
  -> 经营数据
  -> 对话式 Agent
  -> 图表/报告
  -> 洞察/告警
  -> 知识图谱
  -> 审批预审
```

但是，当前各模块的数据模型、权限模型和业务主键还没有完全统一。因此，页面上看起来是一套平台，实际运行时仍有多条相互独立的链路。

## 3. 用户和权限角色

### 3.1 当前可识别的用户身份

后端用户信息至少包含：

- 用户名；
- 角色；
- 部门；
- 用户状态；
- 用户资料；
- 密码哈希或 SSO 身份信息。

前端会保存：

- JWT；
- 用户名；
- 角色；
- 会话缓存。

### 3.2 当前角色方向

当前代码和权限设计中出现以下角色：

| 角色 | 当前定位 | 当前可见能力概况 |
|---|---|---|
| staff | 普通员工 | 登录、问答、部分文档和数据操作，实际 API 权限覆盖不完整 |
| manager | 部门负责人 | 应能查看部门范围的数据、告警和分析，部分能力已设计但未全部落地 |
| admin | 管理员 | 用户管理、文档管理等管理能力，部分接口已接入权限检查 |
| auditor | 审计角色 | 已在权限设计中出现，但当前前端和业务流程未完整体现 |

### 3.3 当前授权方式

系统存在两层安全机制：

1. `AuthMiddleware`：校验请求是否带有效 JWT；
2. `authorize_request()`：根据动作权限、资源属性、密级、部门和所有者做进一步授权。

当前实际问题是：

- 登录认证覆盖面较广；
- 具体动作授权只在部分用户管理 API 中明确调用；
- 文档、数据、图表、导出、告警、洞察、图谱、审批等资源的授权覆盖不一致；
- 资源列表和资源详情未必使用同一套过滤逻辑；
- Agent 工具虽然传递了角色和部门，但并不代表所有 API 和静态文件都完成了同等授权。
- Agent 工具缺少身份上下文时，当前代码存在回退为 `admin` 的路径，这不是安全的默认行为；
- `/static/` 被认证中间件直接放行，图表和报告不具备统一的资源级授权；
- 权限策略异常、主体缺失或资源元数据缺失时，还没有全局统一的“默认拒绝”实现；
- `auditor` 已出现在权限设计中，但用户创建和 SSO 同步允许的角色集合仍不一致。

因此，当前“登录后能访问”与“登录用户有权访问该资源”仍然是两个不同完成度的问题。

当前安全底线应明确为：

```text
没有 Principal -> 拒绝访问受保护资源
没有资源所有权或范围 -> 不能仅凭文件名、session_id 或 URL 访问
授权策略异常 -> 拒绝，不降级为 admin
前端隐藏按钮 -> 不构成后端授权
```

## 6. 文档知识库

### 6.1 用户目标

用户希望把公司的制度、流程、手册、报告等资料放入系统，然后：

- 搜索文档；
- 根据文档提问；
- 查看答案引用；
- 查看原文；
- 下载原始文件；
- 替换或删除旧版本。

### 6.2 当前支持的文件和处理流程

当前文档上传接口位于 `app/api/v1/chat.py`，主要流程是：

```text
接收文件
  -> 保存文件
  -> 解析文本
  -> 文本切块
  -> Embedding
  -> 写入 Chroma
  -> 写入文档目录/版本记录
  -> 异步重建 BM25
```

当前代码中已有 PDF、Word、TXT 等文档加载逻辑，数据文件另有 Excel/CSV 上传入口。

文档元数据支持或计划支持：

- 文件名；
- 版本；
- 密级 `classification`；
- 所属部门 `department`；
- 存储路径；
- 创建时间；
- 文档内容哈希。

必须区分两条当前完全不同的文件处理链路：

```text
知识库文档链路：
PDF / DOCX / DOC / TXT
  -> 纯文本提取
  -> 文本切块
  -> Ollama Embedding
  -> Chroma 向量检索

经营数据链路：
XLSX / XLS / CSV
  -> pandas DataFrame
  -> 预览、统计、排名、分组分析
  -> 图表或报告
```

当前文件能力的准确边界如下：

| 文件或能力 | 当前状态 | 准确说明 |
|---|---|---|
| PDF 普通文本 | 已实现基础能力 | 使用 `pypdf` 提取可复制文本 |
| PDF 表格 | 未实现 | 没有形成表格结构提取、表头识别和表格语义保存 |
| 扫描 PDF、图片型 PDF | 未实现 | 没有 OCR 识别链路 |
| DOCX 普通段落 | 已实现基础能力 | 主要读取段落文本 |
| DOCX 表格 | 不完整 | 没有形成稳定的表格结构化解析 |
| DOC | 基础兼容 | 使用 `olefile` 做粗略文本提取，复杂格式可靠性有限 |
| TXT | 已实现基础能力 | 尝试 UTF-8、GBK、GB2312 |
| Markdown | 未实现 | 当前 `load_document()` 没有 Markdown 专用处理分支 |
| XLSX | 已实现数据分析读取 | 进入 pandas 分析链路，不等于进入知识库 |
| XLS | 代码尝试支持 | 使用 `xlrd`，但当前依赖声明不完整，部署时存在风险 |
| CSV | 已实现数据分析读取 | 支持多种编码尝试，主要服务经营数据分析 |
| Excel/CSV 进入知识库 | 未实现 | 没有按工作表、表头、行列关系和业务语义建立 RAG 索引 |
| 页码、表格、段落定位 | 不完整 | 当前检索结果主要保存文件名和 chunk 索引 |

因此，“当前支持 Excel”只能表述为“支持 Excel/CSV 经营数据读取和分析”，不能表述为“已经具备完整 Excel 知识库解析能力”。

### 6.2.1 与近似项目相比必须补齐的文件处理能力

对方项目已经把多种文件统一纳入知识库处理，而当前项目仍然把“文档问答”和“经营数据分析”分成两条能力链。以下能力是当前明确缺失或不完整、后续必须进入设计和验收范围的部分：

| 能力 | 当前状态 | 后续必须达到的能力 |
|---|---|---|
| PDF 表格解析 | 缺失 | 识别表格区域、表头、行列关系和单元格内容；保留页码、表格编号和原文定位；表格既能预览，也能转为可检索结构 |
| 扫描 PDF / 图片 OCR | 缺失 | 自动识别图片型页面；保存 OCR 文本、页码、识别置信度和失败原因；低置信度内容必须提示用户复核 |
| OCR 后的知识库索引 | 缺失 | OCR 文本经过清洗、分块、向量化和关键词索引后才能参与问答，不能只生成预览文本 |
| Word 表格和结构 | 不完整 | 处理标题、段落、列表、表格和必要的层级关系；表格不能被简单丢弃或拼成无法理解的纯文本 |
| Markdown | 缺失 | 识别标题层级、列表、表格、代码块、链接和引用；切分时保留章节路径，避免回答失去上下文 |
| Excel 作为知识库文档 | 缺失 | 处理工作簿、工作表、表头、合并单元格、行列关系、公式结果和表格范围；支持表格转文本和结构化检索 |
| CSV 作为知识库文档 | 缺失 | 在经营分析之外提供可选的知识库导入模式，保留列名、数据类型、行范围和来源文件 |
| 统一来源定位 | 不完整 | 每个片段应能定位到文件、版本、页码/工作表、表格或章节、行列范围，并能回到原文 |
| 解析质量状态 | 缺失 | 记录解析成功、部分成功、OCR 低置信度、表格异常、编码异常、索引失败等状态和可重试任务 |
| 文档处理模式选择 | 缺失 | 上传时明确选择“知识库问答”“经营数据分析”或“两者都进入”，不能由文件扩展名隐式决定业务含义 |

后续设计不能只增加文件扩展名判断，还必须建立统一的解析结果模型，例如：

```text
原始文件
  -> 文件版本和处理任务
  -> 文档块 / 表格块 / OCR 块 / 数据行块
  -> 来源定位和解析质量
  -> 文本索引、关键词索引、向量索引
  -> 用户可查看的原文、表格和错误报告
```

### 6.5 当前真实完成度

状态：部分实现。

已经形成从上传到索引的主流程，但不能认为是完整的企业知识库管理功能，原因包括：

1. 前端上传时主要提交文件本身，没有完整提交密级、部门、所有者、生效期和敏感级别；
2. 后端同名文档、存储文件名、向量文档名和目录记录之间存在多种命名；
3. 文件系统和向量库的写入不是一个原子事务；
4. 文档版本记录存在，但版本查询、切换、回滚和索引状态管理不完整；
5. 删除、下载、预览、检索的资源级权限没有全部统一；
6. 文档索引失败后的重试、断点续传和任务状态不完整；
7. 生成的静态资源可通过公开静态路径访问，存在证据或文件泄露风险。
8. 上传接口存在一次性读取整个文件的路径，没有统一的文件大小、真实 MIME、魔数、解压后大小和解析资源限制；
9. 文档和数据文件没有统一绑定 `owner_id`、资源范围和 Dataset/Document ID，客户端文件名仍参与资源定位；
10. 文件系统写入、解析、向量写入和目录登记不是原子发布，接口成功不等于索引已经可检索；
11. 删除没有统一清理原文件、索引、缓存、静态产物、Trace 和评测引用的生命周期策略；
12. 文档内容和表格内容进入模型上下文前没有统一标记为不可信证据，尚未形成 Prompt Injection 防护边界；
13. 文档版本记录不等于历史版本可检索，当前没有稳定的 DocumentVersion 与 IndexVersion 绑定。

### 6.6 用户当前不能可靠完成的任务

- 让管理员在上传时明确指定文档密级和部门；
- 让用户只看到自己有权限的文档目录；
- 查看一个文档当前是否已完成解析、向量化和 BM25 建索引；
- 回滚到旧版本并确保旧版本索引被恢复；
- 证明某次回答只使用了当前用户有权访问的文档。

上传和文档处理还不能承诺：

- 可以安全接收任意大小或任意内容的文件；
- 可以识别所有扫描 PDF、复杂 PDF 表格和 Word 表格；
- 可以在失败后自动、幂等地恢复到一致状态；
- 可以在多用户场景下只通过文件名安全定位资源。

|---|---|

### 7.5 当前状态

状态：部分实现。

优势：

- 已经不是单次固定函数调用；
- 支持文档、数据、图表、导出的任务分流；
- 支持并行派发多个 Worker；
- 支持 SSE 和人工确认中断；
- 支持本地模型不可用时的离线回退；
- 支持 LangGraph 检查点。

限制：

1. Worker 主要向 `worker_results` 写入普通字符串；
2. `AgentResult`、Evidence、MetricContext 和 Critic 已定义，但没有贯穿所有 Worker；
3. `reflect_node()` 读取 `agent_results`，而 Worker 不一定填充该字段；
4. 最终答案主要是多个 Worker 字符串拼接，缺少统一结构化汇总；
5. `user_id` 由配置传入，但当前状态中存在回退为 `"default"` 的路径；
6. 模型调用次数较多，查询改写、路由、规划、数据代码、反思、汇总可能重复调用大模型；
7. 重试和反思存在，但执行预算、总超时和模型调用预算还没有成为统一策略；
8. 当 Embedding 服务失败时存在零向量回退，可能产生低质量语义检索结果；
9. 返回图表和报告使用静态路径，不适合敏感数据环境。
10. `search_docs()`、`analyze_data()` 和 `query_data()` 当前存在缺少身份时默认使用 `admin` 的路径，不能视为安全的权限隔离；
11. 检索片段、表格内容和工具结果没有统一的“不可信内容”隔离协议，Prompt Injection 防护尚未闭环；
12. 语义、BM25、RRF 和重排分数没有稳定分字段保存，重排可能覆盖通用 `_score`，调试时无法完整解释各阶段量纲；
13. 当前仍以 Chroma 为主要向量检索实现，PGVector 只是生产目标，不能把目标架构写成当前能力；
14. 查询取消主要是线程事件，不能保证停止模型调用、文件生成、数据库写入或其他后台副作用；
15. 查询缓存没有统一绑定用户权限、知识库版本、数据集版本、Prompt、模型和查询模式；
16. `ThreadPoolExecutor(max_workers=50)` 与本地 14B 模型能力没有形成统一预算，线程数不等于模型并发能力；
17. Redis 队列使用 `BLPOP`，缺少 ACK、租约、重试、死信和幂等，不能作为可靠生产任务系统。

### 7.6 当前问答对用户的真实承诺

当前系统可以尝试回答文档和经营数据问题，但还不能向用户承诺：

- 所有回答都有完整来源；
- 所有来源都在当前用户权限范围内；
- 所有数字都经过统一指标口径校验；
- 所有结论都有可复盘的 Agent 过程；
- 所有回答在相同问题下都具有稳定时延。

## 8. 会话和历史记录

### 8.1 当前能力

后端支持：

- 创建或确保会话；
- 保存用户消息；
- 保存助手消息；
- 查询会话列表；
- 查询会话详情；
- 删除会话；
- 清理 LangGraph 检查点；
- 取消问答请求。

前端同时支持本地保存会话和消息。

### 8.2 当前状态

状态：部分实现，存在数据一致性风险。

当前至少有三类状态来源：

1. 前端 `localStorage`；
2. 后端数据库或内存会话；
3. LangGraph checkpointer。

这会产生以下问题：

- 页面显示的历史与后端记录可能不同；
- 同一会话删除后，检查点、消息和前端缓存可能不同步；
- 浏览器更换设备后无法得到完整历史；
- 用户退出登录时需要清理本地缓存，清理策略和后端状态不是同一事务；
- 前端深度监听消息会在流式回答过程中频繁写本地存储；
- 会话标识、用户标识和 Agent thread_id 的关系需要进一步固定。
- `sessions` 当前没有稳定的 `owner_id` 资源归属字段；
- 会话列表、详情、删除、取消和 Checkpoint 查询没有形成统一的所有者授权闭环；
- 删除会话不代表消息、Checkpoint、缓存、Trace 和相关产物都按同一策略清理；
- Agent 缺少主体时可能落入共享默认身份或默认线程空间，存在跨用户状态混用风险。

会话的生产目标应是：

```text
服务端创建 session_id
  -> 绑定 owner_id / department / visibility
  -> 绑定唯一 Agent thread_id
  -> 所有消息、Checkpoint、Trace 和产物按 session_id 授权
  -> 删除或过期按生命周期策略级联处理
```

### 9.5 `safe_query()` 当前状态

当前使用受限 builtins 加字符串关键字检查，再调用 `eval()` 执行 pandas 表达式。

状态：存在风险。

原因：

- 字符串过滤不是完整语法安全边界；
- `eval()` 本身不适合作为生产级隔离方案；
- 没有独立进程隔离；
- 没有明确的 CPU、内存和执行时间限制；
- 结果大小和中间对象规模控制不足；
- 用户上传数据和模型生成代码共同进入执行环境。

因此当前实现不能称为生产级沙箱。第一版应优先改为结构化查询 DSL；在仍需支持表达式时，至少使用 AST 白名单和独立进程，并具备 CPU、内存、超时、结果大小和强制终止机制。

当前 `build_precheck()` 主要执行：

```text
excess = amount - standard
ratio = excess / standard
有无 evidence
  -> 符合标准
  -> 需人工审批
  -> 无法确认
```

当前 Approval Worker 使用固定的金额、标准和证据，并根据用户问题中是否出现特定关键词调整结果。

### 15.4 当前状态

状态：演示/骨架，不能作为真实审批判断。

核心问题：

1. 标准值由请求方直接传入，不是系统从制度或版本化规则中查询；
2. 金额、部门、费用类型和证据没有形成审批申请实体；
3. 没有申请编号、申请人、申请状态和时间线；
4. 没有制度条款、适用条件、生效日期和版本冲突判断；
5. 没有真正推导审批人；
6. 没有部门负责人、财务、特殊额度等审批节点模型；
7. 没有补材料、转交、驳回、撤回和重新提交；
8. 没有把用户输入数据和原始凭证绑定；
9. Agent 代码存在固定金额和关键词分支；
10. 审批建议没有做到每个结论都有可点击依据；
11. 当前结果只能作为预审提示，不能代表真实审批结果。

## 19. 数据存储和持久化现状

当前项目使用多种存储方式：

| 数据 | 当前存储 |
|---|---|
| 用户、部分会话、文档目录、告警 | PostgreSQL 可用时写数据库 |
| 向量和文档片段 | Chroma，缺失依赖时有 JSON 回退 |
| 原始文档 | 本地 `documents` 目录 |
| Excel/CSV | 本地 `data` 目录 |
| 图表 | 本地 `static/charts` |
| 导出报告 | 本地 `static/exports` |
| 知识图谱 | 当前主要为内存字典 |
| 无数据库回退状态 | 多处使用内存列表或字典 |
| 前端历史会话 | 浏览器 `localStorage` |
| Agent 执行状态 | LangGraph checkpointer，数据库可用时可持久化 |

当前真实数据库和存储组合不是“MySQL + PostgreSQL + PGVector”，而是：

```text
PostgreSQL
  -> 用户、部分会话、文档目录、告警、长期记忆、部分业务记录

Chroma PersistentClient
  -> 文档片段和向量

Redis
  -> 队列、缓存和 Worker 协调

本地文件系统
  -> 原始文档、Excel/CSV、图表、报告和 Chroma 数据目录

内存回退
  -> PostgreSQL、Redis 或其他依赖不可用时的开发态降级
```

当前没有发现以下生产实现：

- MySQL 驱动或 MySQL 业务库；
- Tortoise ORM；
- PGVector 扩展；
- PGVector 向量表或 LangChain PGVector 集成；
- 将 Chroma 中现有向量自动同步到 PostgreSQL 的机制。

`PostgresSaver` 只表示 LangGraph 检查点可以使用 PostgreSQL 持久化，不表示系统已经使用 PGVector。Chroma 和 PGVector 都可以保存向量，但它们是两种不同的向量存储实现。

### 19.1 推荐的生产目标存储架构

当前项目的长期目标不应继续停留在“PostgreSQL + Chroma + 文件目录”的过渡组合。结合私有化部署、权限过滤、文档版本、审计和后续多用户运行，推荐目标架构为：

```text
PostgreSQL + PGVector
  -> 用户、权限、会话、文档、文档版本、解析任务、数据集、指标、告警、审批、审计
  -> 文档块、表格块、OCR 块及其向量

本地文件存储
  -> 原始文档、原始表格、OCR 中间产物、图表、报告和导出文件

Redis
  -> 异步解析任务、索引任务、队列、缓存和短期任务状态
```

这不是对当前实现的误述，而是后续生产化目标：

| 组件 | 当前状态 | 目标职责 |
|---|---|---|
| PostgreSQL | 已使用 | 继续作为业务主库，统一资源元数据、权限、版本、任务和审计 |
| Chroma | 已使用 | 作为当前过渡向量库；迁移完成后不再作为生产主向量库 |
| PGVector | 当前未实现 | 作为 PostgreSQL 内的生产向量存储，与文档权限和版本在同一数据边界内 |
| 本地文件存储 | 已使用 | 保存原始文件和大体积产物，不把原始文件直接塞入数据库 |
| Redis | 已使用或按部署启用 | 承担异步任务、队列、缓存和任务协调，不作为业务事实数据库 |
| MySQL | 当前未实现 | 不是单企业私有化部署的必需组件；只有接入客户既有 MySQL 业务系统时才单独引入 |

PGVector 迁移必须和模型版本绑定设计。不同 Embedding 模型的向量维度不能直接混在同一向量空间中，因此每个知识库应绑定 Embedding 模型和索引版本；更换模型时建立新索引、完成验证后再切换生效版本，不能直接覆盖旧向量。

当前主要一致性问题：

- 数据库、文件系统、向量库没有统一事务；
- 文件删除不一定同步删除目录、索引、版本和相关产物；
- 内存回退适合开发或离线验证，不适合多实例生产；
- 图表和报告没有进入统一资源表；
- 会话存在前端、后端和 LangGraph 三份状态；
- 知识图谱没有可靠持久化；
- 多个模块在运行时执行 `CREATE TABLE IF NOT EXISTS` 或 `ALTER TABLE ... ADD COLUMN`，没有统一 Schema 版本、迁移锁、失败阻断和回滚；
- 多个模块直接创建 PostgreSQL 连接，没有统一连接池、连接超时、查询超时和跨资源事务边界；
- 审计日志主要保存在进程内存，服务重启后不能作为完整审计记录恢复；
- 当前备份脚本主要压缩本地目录，不能单独证明 PostgreSQL、权限、Trace、评测和 Redis 任务状态可完整恢复。

## 23. 当前最重要的事实判断

### 23.1 已经有价值的基础

当前项目并不是空壳，已经具备以下有价值基础：

- 文档解析、向量化和检索链路；
- BM25、RRF、重排等检索增强组件；
- 本地模型和私有化部署方向；
- 多 Agent 调度框架；
- Excel/CSV 数据分析和图表输出；
- SSE 流式问答；
- 版本目录、审计、权限、质量和部署相关基础模块；
- 主动告警、知识图谱、审批助手的业务方向。

### 23.2 当前最大结构性问题

当前最大问题不是缺少更多页面，而是以下事实尚未统一：

1. 数据从哪里来；
2. 数据属于谁；
3. 谁可以看；
4. 这项数据代表哪个期间；
5. 这个指标如何计算；
6. 这个结论依据什么；
7. 这个结论是否被审核；
8. 这个文件、图表、洞察或审批结果如何追踪；
9. 用户完成任务后下一步是什么；
10. 失败后如何重试、纠正和恢复。

### 23.3 当前不应继续默认的产品承诺

在设计修正完成前，不能默认对外承诺：

- 所有模块都使用用户上传的真实数据；
- 所有页面都反映当前权限范围；
- 所有审批建议都来自真实制度；
- 所有图表和报告都可以安全分享；
- 所有 Agent 结论都可以完整复盘；
- 所有模块重启后都保持状态；
- 所有模型失败都能安全、可解释地降级。

## 24. 本文档之后的设计输入

后续设计修正文档必须至少解决以下问题：

1. 以用户任务而不是页面数量重新组织功能；
2. 建立文档、数据集、指标、证据、洞察、审批、图表和报告的统一资源模型；
3. 把所有输入都改为有来源、有版本、有权限的数据；
4. 明确每个状态的创建、处理中、成功、失败、取消、过期和删除；
5. 明确普通用户、部门负责人、管理员、审计人员和系统 Agent 的边界；
6. 明确每个结论的证据、口径、时间范围和置信度；
7. 审批功能必须从“计算题”改为“证据驱动的预审工作流”；
8. 洞察和告警必须统一，避免两套重复异常逻辑；
9. 设计管理员可操作的检索调试、评测和版本对比闭环；
10. 建立 Agent Run、Agent Step、Tool Call、Model Call 和 Retrieval Trace 的可观测性闭环；
11. 建立后台配置中心的草稿、校验、评测、发布、回滚和审计流程；
12. 明确哪些功能允许离线回退，哪些功能必须失败并提示；
13. 将静态文件下载改为受控资源访问；
14. 设计过程中不能使用固定金额、固定部门、固定指标、固定样例作为真实业务逻辑。

## 25. 盘点结论

当前项目可以描述为：

> 一个已经具备企业知识问答、经营数据分析和多 Agent 技术基础，同时包含 Dashboard、洞察、告警、知识图谱和审批助手雏形的私有化企业智能平台。

当前还不能描述为：

> 一个所有业务模块都由真实企业数据驱动、权限闭环完整、审批结果可信、所有结论可追溯、所有资源可审计的生产级企业决策系统。

下一份文档不应继续罗列零散改进点，而应基于本文件重新设计：

```text
用户任务
  -> 业务对象
  -> 数据来源
  -> 权限边界
  -> 状态流转
  -> Agent 行为
  -> 证据与结果
  -> 人的确认
  -> 审计与复盘
```

## 28. 查询速度问题的当前诊断

### 28.1 已观察到的实际时延

现有日志已经出现以下事实：

- 数据分析请求总耗时约 47.6 秒；
- 文档问答请求总耗时约 183.3 秒；
- 文档问答中出现一次约 60 秒模型请求超时；
- 查询改写完成后又发生多轮检索；
- Supervisor、Worker 和最终汇总均可能调用本地 14B 模型；
- 数据分析工具会遍历数据目录并重新读取多个文件；
- 普通会话携带 `session_id` 时，现有问答缓存基本不会命中。

因此当前时延不能归因于单一硬件问题。核心瓶颈是“默认链路过重 + 模型调用重复 + 文件读取重复 + 失败等待时间过长”。

### 28.2 当前一次查询可能经过的步骤

```text
追问重写
  -> 意图分类
  -> 记忆读取
  -> Planner
  -> Supervisor 路由
  -> Worker Agent
  -> Worker 工具
  -> 查询改写
  -> 多个查询的语义检索和 BM25
  -> RRF
  -> Cross-Encoder
  -> Worker 生成
  -> Supervisor 汇总
  -> Reflect
  -> Synthesize
```

这条链路适合复杂问题，不适合所有普通问题。

### 28.3 速度设计原则

后续性能改造必须遵守：

1. 简单问题不走完整 Multi-Agent；
2. 规则能确定的路由不调用大模型；
3. 能直接用 pandas 计算的排名、合计、均值、最大值、最小值和分组汇总不调用大模型生成代码；
4. 查询改写只在原始召回不足或问题存在指代时触发；
5. Cross-Encoder 只重排有限候选，不默认重排所有查询扩展结果；
6. 反思和长期记忆摘要不能阻塞主回答；
7. 每个阶段必须记录独立耗时；
8. 超时必须按阶段降级，不能让普通问题无条件等待完整模型超时；
9. 任何缓存必须包含用户权限范围、部门、密级、数据/文档版本、策略版本和模型版本；
10. 加速不能以跳过权限、证据或数据口径校验为代价。

### 28.4 查询分级

| 模式 | 适用问题 | 处理链路 |
|---|---|---|
| 快速 | 单一制度事实、单字段排名/合计/平均值、简单闲聊 | 规则路由 + 一次检索或直接计算 + 必要时一次回答 |
| 标准 | 普通文档问答、单数据集分析、简单图表 | 一次路由 + 原问题检索/计算 + 按需改写或重排 + 一次回答 |
| 深度 | 跨文档、跨数据集、制度与经营数据结合、复杂审批建议 | Planner + 多 Agent + 证据审查 + 结构化汇总 |

模式不是按固定金额或固定部门判断，而是根据问题意图、涉及资源数量、计算复杂度、证据要求和用户主动选择共同决定。

### 28.5 模型分层原则

第一版模型管理必须支持按用途选择模型，而不是全系统只能配置一个模型：

| 用途 | 选择原则 |
|---|---|
| 快速路由 | 优先规则；需要模型时选择本机可用的轻量对话模型 |
| 查询改写 | 选择响应快、上下文能力够用的本机对话模型 |
| 简单数据解释 | 选择轻量或中等本机对话模型 |
| 复杂综合回答 | 选择本机可用的高质量模型 |
| Embedding | 只选择被识别并验证支持 Embedding 的本机模型 |
| 重排 | 使用已配置的本地重排模型；不能把普通对话模型误当成重排模型 |

具体选择不能写死为 `7B`、`14B` 或某个固定名称。系统应根据本机已发现模型、能力测试、管理员选择和运行资源动态决定。

```text
answer_generation
critic
synthesize
total
```

验收不使用未经实测的绝对承诺，而使用同一设备、同一数据、同一问题集的前后对比：

- 简单数据问题是否绕过完整 Agent；
- 简单文档问题是否不默认多查询扩展；
- 失败模型是否不再额外等待一个完整长超时；
- 数据文件是否只加载指定数据集；
- P50、P95、错误率和降级率是否改善；
- 回答质量、证据覆盖和权限边界不能下降。

## 29. 第一版 Ollama 本机模型自动发现与选择

### 29.1 范围约束

第一版只支持 Ollama，不接入 LM Studio、vLLM、Xinference 或其他模型服务。第一版不负责自动下载模型，只负责发现和管理本机 Ollama 已安装、可访问的模型。

目标是解决：

```text
当前只固定使用一个 OLLAMA_MODEL
```

升级为：

```text
连接本机 Ollama
-> 读取已安装模型
-> 获取模型详情
-> 判断可用能力
-> 管理员选择用途
-> 保存选择
-> 运行时按用途读取
```

### 29.2 用户任务

管理员可以：

1. 查看本机 Ollama 当前已安装模型；
2. 刷新模型列表，发现后来安装的模型；
3. 查看模型名称、大小、参数或量化等 Ollama 提供的信息；
4. 对模型执行连通性测试；
5. 查看模型被系统识别为哪些能力；
6. 为不同任务选择不同模型；
7. 保存模型用途配置；
8. 在不修改代码的情况下让后续请求使用新配置；
9. 查看当前生效配置和最近一次测试结果；
10. 在选定模型不可用时得到明确错误或安全降级提示。

普通用户不直接修改全局模型配置。模型选择属于系统运行配置，应由管理员或具备模型管理权限的角色操作。

### 29.3 模型用途

第一版至少区分以下用途：

```text
fast_chat_or_routing
standard_chat
complex_reasoning
embedding
rerank
```

其中：

- `fast_chat_or_routing`、`standard_chat`、`complex_reasoning` 由 Ollama 本机对话模型承担；
- `embedding` 只允许通过能力检测的 Embedding 模型；
- `rerank` 可以登记本地重排模型，但不能因为模型出现在 Ollama 列表中就默认认为它支持重排；
- 同一个模型可以被管理员分配多个用途，但系统要提示资源竞争和性能影响；
- 一个用途可以有主模型和备用模型，但备用模型必须经过相同能力验证；
- 没有通过验证的模型不能被标记为可生效模型。

### 29.4 自动识别原则

模型能力识别分为两层：

1. **静态识别**：读取 Ollama 模型详情、模型名称、模板、参数信息和已知元数据；
2. **主动验证**：用最小请求测试对话、结构化输出、Embedding 或其他能力。

静态名称只能作为候选判断，不能作为最终依据。例如名称中包含 `embed` 不足以证明接口行为符合当前 Embedding 适配器要求。

识别结果必须包含：

- 模型名称；
- Ollama 标签或标识；
- 是否存在；
- 是否可连接；
- 最近测试时间；
- 测试耗时；
- 对话能力；
- Embedding 能力；
- 工具/结构化输出能力；
- 是否被管理员启用；
- 失败原因；
- 能力识别来源：静态推断或主动测试。

### 29.5 配置生效原则

模型配置不能只写入进程启动时读取的环境变量。运行时应有一个可查询、可审计、可更新的配置来源，并包含：

- 用途；
- 主模型；
- 备用模型；
- 配置版本；
- 修改人；
- 修改时间；
- 生效状态；
- 最近测试状态。

修改配置后的行为：

- 新请求使用新配置；
- 正在执行的请求继续使用开始时绑定的模型配置版本；
- 配置变更不能导致正在执行的请求中途切换模型；
- 模型删除、卸载或不可访问时，新请求必须明确报告不可用原因；
- 不能静默切换到远程模型；
- 远程模型回退必须由独立配置显式开启，私有化默认关闭。

### 29.6 与性能方案的关系

Ollama 模型管理不是单独的设置页面，而是性能分级方案的基础：

```text
本机可用模型列表
  -> 能力验证
  -> 管理员按任务选择
  -> 快速/标准/深度查询按用途取模型
  -> 记录模型版本和耗时
  -> 质量与性能对比
```

模型选择不能只看参数规模，还应结合：

- 本机 CPU/GPU/显存；
- 模型加载时间；
- 首 token 延迟；
- 生成速度；
- 上下文长度；
- 工具调用稳定性；
- 结构化输出稳定性；
- Embedding 维度兼容性；
- 并发请求下的资源占用。

### 29.7 Ollama 功能验收方向

第一版完成的最低标准：

1. Ollama 不可用时，管理页面明确显示连接失败原因；
2. Ollama 可用时，能列出本机实际已安装模型；
3. 新安装模型经刷新后可以出现，不需要修改代码；
4. 对话模型和 Embedding 模型不能仅凭名称混用；
5. 管理员可以为不同用途保存不同模型；
6. 配置修改后新请求使用新配置，不要求重启应用；
7. 卸载当前生效模型后不能静默使用错误模型；
8. 模型调用日志记录用途、模型、配置版本、耗时和结果状态；
9. 模型选择和测试操作进入审计日志；
10. 选定模型不满足能力要求时不能保存为生效配置。

## 30. 评测体系现状与升级目标

### 30.1 用户目标

管理员需要知道一次改动是否真的让系统变好，而不是只凭主观感受判断。评测中心应支持：

- 维护真实业务评测用例；
- 固定知识库、数据集、模型、Prompt 和检索策略版本；
- 批量运行同一批问题；
- 比较不同方案的正确性、证据、权限和时延；
- 从失败用例直接定位到检索阶段、Agent 步骤或数据计算；
- 将用户点踩、人工纠正和失败审批预审沉淀为新用例。

### 30.2 当前已有

当前源码和测试资料已经提供评测基础：

| 能力 | 当前证据 | 当前结论 |
|---|---|---|
| 评测集文件 | `tests/fixtures/business_evaluation_30.jsonl` | A：已有 30 条业务评测样例 |
| 基础评测函数 | `app/quality/eval.py` | A：支持答案、证据、分类和耗时的基础统计 |
| 记录答案评测 | `app/quality/runner.py` | A：可读取已保存答案并生成 JSON 报告 |
| provenance 统计 | `app/quality/provenance.py` | A：可汇总 Worker、证据和可信度 |
| 评测测试 | `tests/test_quality_platform.py`、`tests/test_quality_runner.py` | B：有测试覆盖，本次未运行 |
| 完整四项 RAG 指标 | 未发现独立实现 | E：不能称为已经实现 |
| 管理员评测工作台 | 未发现 API 和页面闭环 | E：属于后续目标 |

当前评测更接近：

```text
读取预先保存的答案
  -> 字符串包含或相等判断
  -> 是否存在证据
  -> 统计分类结果和延迟
```

它还不是“选择策略后自动调用完整系统并形成可比较实验”的质量平台。

### 30.3 当前缺失和风险

- 没有将一次评测绑定到知识库版本、数据集版本、模型配置版本、Prompt 版本和检索策略版本；
- 没有独立的评测用例、评测运行、单条结果和报告实体；
- `evaluate_evaluation_set()` 主要依赖 `must_contain` 或答案包含关系，不能充分判断语义正确性；
- 没有 Context Recall、Context Precision、Faithfulness、Answer Relevancy 的完整实现；
- 没有通过来源片段 ID 集合计算“该找的片段是否找回”；
- 没有记录正确片段的排名变化、过滤前后数量和最终上下文；
- 没有统一评测数据分析、图表、审批、权限拒绝和工具调用；
- 没有评测失败自动关联 Agent Trace 和慢阶段；
- LLM-as-judge 的裁判模型、温度、提示词和版本没有成为实验元数据；
- 当前没有管理员查看历史报告、复制实验、比较版本和回归趋势的入口。

### 30.4 推荐评测闭环

评测应拆成四层，不能只看最终答案：

```text
检索质量
  -> Context Recall
  -> Context Precision
  -> 首个正确片段排名
  -> Top-K 命中率
  -> 检索阶段耗时

回答质量
  -> Faithfulness
  -> Answer Relevancy
  -> Answer Correctness
  -> Unsupported Claim Rate

企业任务质量
  -> 数据计算准确性
  -> 指标口径准确性
  -> 图表数据准确性
  -> 审批依据完整性
  -> 工具选择和调用成功率

系统质量
  -> 权限拒绝准确率
  -> 越权证据泄露率
  -> P50/P95 延迟
  -> SSE 中断率
  -> 模型降级率
  -> 任务失败率
```

推荐实体关系：

```text
EvalDataset
  -> EvalCase
  -> EvalRun
  -> EvalResult
  -> EvalReport
```

每次 `EvalRun` 至少固定：

- 评测集版本；
- 知识库和文档索引版本；
- 数据集版本；
- 模型及其能力配置版本；
- Prompt 版本；
- 检索策略版本；
- Agent 运行模式；
- 裁判模型、温度和提示词版本；
- 运行环境、时间和操作者。

规则校验优先于模型裁判：

- 数字、排序、合计和图表数据使用确定性校验；
- 来源召回使用期望片段 ID 集合；
- 权限使用授权规则测试；
- LLM 只评价忠实性、相关性和表达质量等难以完全规则化的内容。

### 30.5 相比近似项目的改进方向

近似项目的优势是 RAG 评测闭环较完整。当前项目不应只复制四个指标，还应把企业任务纳入同一份报告：

- 文档问答是否正确；
- Excel 计算是否正确；
- 指标口径是否正确；
- 图表是否使用真实数据；
- 审批建议是否有制度依据；
- 用户是否被正确拒绝访问；
- Agent 是否调用了合适的工具；
- 总耗时是否超过该任务模式预算。

这样评测对象从“RAG 回答”扩展为“企业任务完成质量”。

### 30.6 验收标准

1. 同一评测集可以绑定不同策略、模型和 Prompt 版本重复运行；
2. 同一用例能同时看到答案、证据、检索排名、Agent Trace 和耗时；
3. 报告至少区分检索质量、回答质量、企业任务质量和系统质量；
4. 评测结果可以按版本并排比较，不能只覆盖上一份报告；
5. 数字、来源集合和权限结果优先使用确定性校验；
6. 每条失败结果都能定位到具体阶段或具体证据；
7. 评测报告本身受到管理员权限保护，不能泄露敏感答案和原文。

## 31. Agent 可观测性现状与升级目标

### 31.1 用户目标

用户和管理员需要知道：

- 系统当前正在做什么；
- 为什么调用某个 Agent 或工具；
- 哪一步耗时最长；
- 哪一步失败或被重试；
- 最终答案使用了哪些证据；
- 失败后系统是降级、重试还是停止。

### 31.2 当前已有

当前项目已有以下基础：

| 能力 | 当前证据 | 当前结论 |
|---|---|---|
| LangGraph 编排 | `app/agents/orchestrator.py` | A：存在节点、Worker、反思和汇总 |
| SSE 步骤事件 | `app/api/v1/chat.py` | A：当前请求可以接收步骤状态 |
| AgentState | `app/agents/state.py` | A：已有 `agent_results`、`worker_results`、`trace_events` 等字段 |
| AgentResult/Critic | `app/agents/contracts.py`、`app/agents/critic.py` | A：结构化契约和规则审查雏形存在 |
| 检查点 | `PostgresSaver` / `MemorySaver` | A：具备流程检查点方向 |
| 性能统计 | `app/common/performance.py` | A：有进程级平均值、P95 和错误率统计 |
| 脱敏配置 | `app/common/tracing.py` | A：有敏感字段脱敏和 LangSmith 配置 |
| 独立运行历史 | 未发现 `agent_run`、`agent_step` 持久化模型 | E：尚未形成后台历史回放 |

### 31.3 当前问题

当前存在两条没有完全接通的结果链：

```text
Worker
  -> worker_results: 普通字符串
  -> Synthesis: 字符串拼接

结构化契约
  -> agent_results: AgentResult
  -> Reflect/Critic: 只在部分结果可用时工作
```

同时：

- `trace_events` 主要存在于运行状态或 SSE 过程中，不是完整的独立运行记录；
- SSE 步骤只服务当前页面，页面关闭后管理员无法按运行查询；
- `audit.py` 当前主要是进程内列表，不适合作为长期审计库；
- 没有统一记录排队、模型、检索、工具、权限过滤和生成阶段耗时；
- 没有记录每一步开始时绑定的模型、Prompt、策略和资源版本；
- 没有把 `Tool Call`、`Model Call` 和 `Retrieval Trace` 从普通日志中分离出来；
- 没有统一保存重试原因、降级原因、取消原因和最终状态；
- 不能稳定回答“慢在模型、检索、数据加载还是等待队列”。

### 31.4 推荐运行追踪模型

```text
AgentRun
  -> AgentStep
      -> ToolCall
      -> ModelCall
      -> RetrievalTrace
  -> EvidenceLink
  -> ReviewResult
  -> FinalArtifact
```

`AgentRun` 表示一次完整用户任务，至少包含：

- `run_id`；
- `user_id`、`session_id`；
- 原始问题和规范化问题；
- 查询模式：快速、标准或深度；
- 请求开始时绑定的模型、Prompt、知识库、数据集和策略版本；
- 当前状态：排队、运行中、等待确认、成功、部分成功、失败、取消、超时；
- 总耗时、降级状态和错误摘要。

`AgentStep` 至少包含：

- 节点名称和 Worker；
- 步骤顺序、开始时间和结束时间；
- 输入摘要和输出摘要；
- 状态、耗时和错误；
- 使用的模型和配置版本；
- 证据数量、产物数量和重试次数。

`ToolCall` 至少包含：

- 工具名称；
- 脱敏后的入参摘要；
- 返回状态和结果摘要；
- 权限决策；
- 开始时间、耗时和错误原因。

`RetrievalTrace` 至少包含：

- 原始查询和改写查询；
- 知识库与索引版本；
- 语义、BM25、RRF、重排各阶段候选数量；
- 各阶段分数和排名；
- 权限过滤前后数量；
- 最终注入上下文的片段 ID。

### 31.5 相比近似项目的改进方向

近似项目主要展示 Agent Run/Step 时间线。当前项目应将时间线扩展为：

```text
任务过程
 + 性能过程
 + 工具过程
 + 检索过程
 + 证据过程
 + 权限过程
 + 质量审查过程
```

这样不仅能回答“Agent 做了什么”，还能回答“为什么得到这个答案、是否越权、哪一步应该优化”。

### 31.6 验收标准

1. 请求结束后仍可按权限查询完整运行记录；
2. 每个步骤都具备开始、进行中、成功、部分成功、失败或取消状态；
3. 每个模型调用、工具调用和检索阶段都有独立耗时；
4. 重试、降级、权限拒绝和人工确认都能在时间线上看到；
5. 最终答案中的证据、图表和报告都能回指到对应步骤；
6. Trace 不记录密码、JWT、API Key 和不必要的完整敏感原文；
7. 多用户、多会话之间的 Trace 不能串线；
8. 管理员能按慢请求、失败 Worker、模型和策略版本筛选运行记录。

## 32. RAG 检索调试现状与升级目标

### 32.1 当前已有

`app/rag/retrieval_pipeline.py` 已有：

- 查询改写和子问题拆分；
- 语义召回；
- BM25 召回；
- 并行执行；
- RRF 融合；
- Cross-Encoder 重排；
- 去重；
- 权限过滤入口。

这说明当前项目已经有可调试的检索管线基础，但没有形成用户可操作的调试产品。

### 32.2 当前缺失

- 没有检索调试 API 和后台页面；
- 不能选择知识库、文档版本和检索策略版本；
- 不能查看每个改写问题；
- Chroma 结果没有稳定返回可解释的语义分数；
- BM25 结果没有稳定携带 BM25 分数；
- RRF 只排序，没有统一保存 RRF 分数；
- Cross-Encoder 使用 `_score`，可能覆盖前一阶段语义；
- 没有保存排名变化、过滤前后数量和最终上下文；
- 去重主要按内容前 120 字符，存在不同片段被误合并的风险；
- 召回失败、Embedding 失败和重排缺失没有统一展示；
- 不能用同一个问题并排运行多套策略；
- 不能把检索结果直接送入评测报告比较。

### 32.3 推荐调试台

管理员输入一个问题后，可以选择：

- 知识库；
- 文档或索引版本；
- 查询模式；
- 最多四套检索策略；
- Embedding 模型和重排模型配置；
- 权限主体或测试用户范围。

系统按以下结构返回：

```text
原始问题
  -> 查询改写
  -> 语义召回
  -> BM25 召回
  -> RRF 融合
  -> 重排
  -> 权限过滤
  -> 最终上下文
  -> 可选答案生成
```

每个结果必须使用独立字段：

```text
semantic_score
bm25_score
rrf_score
rerank_score
rank_before
rank_after
score_type
```

不能继续用一个会被覆盖的通用 `score` 表示不同量纲。

建议的四套默认实验只是可选模板，不是写死的业务规则：

```text

策略 B：语义 + BM25
策略 C：语义 + BM25 + RRF
策略 D：完整策略，包括按配置启用的改写、重排和父块回填
```

### 32.4 必须结合你的项目增加的内容

除了对方的 RAG 调试能力，当前项目还必须显示：

- 文档和经营数据的资源类型；
- 文档版本、数据集版本和索引版本；
- 权限过滤前后的候选变化；

### 32.5 验收标准

1. 同一问题可以运行并比较多套策略；
2. 每套策略显示改写、各路召回、融合、重排和最终上下文；

至少需要版本化的配置包括：

### 37.3 本轮新增的安全和可靠性边界

以下内容在上一版文档中没有形成足够明确的当前状态，本轮正式加入：

1. **主体缺失不再视为管理员**：任何文档、数据、导出、删除和 Agent 工具调用都必须有明确 Principal；系统后台任务必须使用显式、最小权限的 system principal。
2. **资源必须有稳定 ID**：文件名、URL、前端传入的 `session_id` 和 `data_filename` 只能作为查询线索，不能作为授权依据。
3. **上传必须先安全接收，再解析和发布**：文件大小、真实类型、魔数、压缩展开规模、页数、行数和解析时长都必须有上限。
4. **文档和表格是数据，不是指令**：检索片段、OCR 文本、单元格内容和外部应用输入都必须按不可信内容处理。
5. **取消不是删除**：请求取消、任务取消、已产生副作用和资源删除必须使用不同状态，不能只设置一个线程事件。
6. **队列结果不是业务事实**：Redis 中的任务状态和结果必须有幂等键、过期策略和持久化业务记录，不能只依赖字符串缓存。
7. **降级必须可见**：模型不可用、Embedding 失败、索引不完整、证据不足或使用演示数据时，结果必须带结构化状态和用户可见警告。
8. **金额、时间和指标不能靠默认值**：金额使用 Decimal 和币种，时间使用明确时区和期间，指标使用版本化 MetricDefinition。
9. **删除必须覆盖所有副本**：原文件、解析块、向量、BM25、缓存、Artifact、Trace、评测引用和备份副本都要有明确的软删除、保留期或硬删除规则。
10. **生产密钥不能使用默认值**：JWT 密钥、初始管理员密码和外部凭证必须通过安全初始化注入；缺失时阻断生产启动，不能写入日志或回退为公开默认值。

### 37.5 与其他 Agent 的协作边界

- 本次修订不修改 `frontend/`；
- 前端 Agent 只需依据本文件和后续 API/SSE 契约调整显示、状态和错误处理；
- 后端必须先稳定 Principal、资源 ID、错误码、SSE 事件和 Artifact 下载契约，再让前端接入；
- 前端按钮隐藏、路由守卫和本地角色缓存不能被当作后端授权；
- 任何新增页面都必须使用真实资源、版本、权限和状态，不得重新引入固定 rows、固定金额、固定部门或固定阈值；
- 如果后续代码实现与本文档冲突，应先更新“当前功能文档”和修改记录，再继续扩展功能。

### 37.6 本轮结论

当前项目的准确定位仍然是：

> 已具备企业知识问答、经营数据分析、图表、报告和 Multi-Agent 的开发基础，但尚未形成资源隔离、任务可靠、指标可信、证据可追溯和可恢复的生产闭环。

因此后续实现顺序必须先处理权限、资源模型、迁移、上传安全、队列、模型调用预算和可观测性，再继续扩展 Dashboard、审批、洞察和复杂 Agent 能力。

### 38.2 本轮发现并修复的真实缺陷

下列问题的共同点是：在离线 JSON 回退路径上永远不会出现，只有连真实服务或真实镜像才会暴露。

1. `app/storage/persistence.py` 用 `dict(row)` 读取元组行，导致第二个 trace 事件起整条执行账本写入全部抛 `PersistenceWriteError`；同一适配器还按不存在的 `created_at` 排序四张 Agent 表。修复为 `_as_record()` 与按表 `order_column`。
2. `Dockerfile` 基础镜像 `python:3.14-slim` 违反 `requires-python = ">=3.11,<3.14"`；`uv sync` 装进 `/app/.venv` 而 `CMD` 用裸 `uvicorn`；缺 `COPY migrations`/`COPY scripts`；并把 `documents/`、`data/`、`chroma_db/`、`static/` 烤进镜像。已全部修正并改为非 root 运行。
3. Compose 用 `postgres:16-alpine`，该镜像不含 `vector` 扩展，迁移 `0001` 的 `CREATE EXTENSION vector` 在全新安装上必然失败。改为 `pgvector/pgvector:pg16`。
4. `deploy/nginx.conf` 原本是整份 `http{}` 配置却被拷进 `conf.d/default.conf`（`nginx -t` 必失败），且 `location /static/ { alias ... }` 让图表和报告绕过授权（违反边界规则 15），`/health` 由 nginx 直接返回 `200 "OK"` 属假绿，`upstream 127.0.0.1:8001..8008` 在容器间不可达，`limit_req 10r/m` 会掐断前端 3s 轮询。重写为真正的 `conf.d` 片段：代理 `/api/`、真实探测 `/api/v1/health`、对 `documents|data|logs|chroma_db|static|uploads|exports` 一律 `deny`，不再有公开 `/static`。
5. 两份 Compose 各自复制一套拓扑且已经分叉。现改为根 `docker-compose.yml` 是唯一权威栈（`postgres`/`redis`/`ollama`/一次性 `migrate`/`backend`/`worker`/`scheduler`/`frontend`），`deploy/docker-compose.server.yml` 只是叠加层。
6. 调度器原先挂在 FastAPI `startup`，后端副本和 `start_workers.sh` 的八个实例会重复巡检与日报。改为 `SCHEDULER_ENABLED`（生产默认关）加独立进程 `deploy/scheduler.py`。
7. 代码里写死默认模型名（`app/common/model_config.py` 与 `app/common/monitoring.py` 的 `qwen2.5:14b`）违反“模型名属于配置”的边界规则。改为显式配置优先、否则从本机 Ollama 发现、再否则为空并诚实降级。
8. `app/main.py` 的 `allow_origins=["*"]` 改为 `CORS_ALLOW_ORIGINS` 白名单，生产未配置即启动失败。
9. `/api/v1/queue/status/{id}` 在 `failed`/`dead` 分支不返回失败原因，违反“长任务必须给出失败原因”。新增 `ReliableQueue.failure()` 并在所有分支返回 attempts/last_error/max_attempts，契约文档同步。
10. `pyproject.toml` 补 `testpaths = ["tests"]`，避免 `tmp/*_test.py` 被收集成 3 个采集错误而掩盖真实回归。
11. 环境文件转义冲突（本轮容器校验时发现的真实缺陷）：Compose 会对 env 文件做变量替换，而 python-dotenv 按字面读取。仓库 `.env` 里的 `AUTH_PASSWORD_HASH` 含 bcrypt 的 `$`，用 `docker compose config` 实测被改写成残缺值（中间段被替换为空），一旦照此部署，登录会永久失败且没有任何报错。修复：容器只读 `deploy/.env.server`（`$` 必须写成 `$$`），开发 `.env` 不再进 Compose，并新增 `scripts/check_deployment_env.py` 预检（只报键名和列号，不打印值）。
