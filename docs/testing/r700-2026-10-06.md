## 3. 被否掉的两种做法（取证，不是偏好）

**甲：让 `upload_excel` 直接委派 `app/api/v1/chat.py::upload_document`。**
- 先撞禁区：`app/api/v1/chat.py` 是工单点名禁区，委派要在两枚路由之间搬身份与错误语义（`upload_document` 允许 principal 为 None ⇒ 记成无主 legacy 行），一次 upload-excel 长出两套权限判定。
- 形状不合：`upload_document` 把字节按 uuid 另存进 `DOCUMENTS_DIR`（`app/documents/file_security.py::build_storage_path`）并 `peek_next_document_version` 长一枚**文档版本行**；数据集那一路全程按文件名寻址（`GET /api/v1/data-files/{filename}/preview`、下载、删除都认名字）。委派 = 给同一份文件造第二副本 + 第二套版本语义，那正是 **R687 的零拷贝问题**，不归本单裁。
- 状态码不合：`upload_document` 解析失败回 **500** `document_parse_failed`，而判据②要 `upload_excel` 的状态码不动。
- 盘面脏到仓库：conftest 钉了 `DATABASE_URL` 与模型端口，**没钉** `DOCUMENTS_DIR`；委派形态的写入会落到仓库里的 `./documents` 与 `./data/index-versions.json`（R134 那一族写回闸门盯着的形状）。

**乙：新模块自己枚 `DocumentRetriever()`。**
- 热集与闸门都长在句柄内部：私枚句柄把新行放进持久库，而**答题那枚句柄**的热子集不知道有这批行，要到下次进程启动才看得见——「上传成功但检索查不到」正是判据①要治的病形。故 `app/api/v1/data.py::_knowledge_base_retriever` 向 `app/api/v1/chat.py::retriever` 借同一枚句柄，import 保持 lazy（路由不许为它把 chat 的导入图拉进来）。

## 5. 交回总控的六格（本单故意没做／需要落账，不是漏）

1. **目录行与索引版本发布没做**：`_record_uploaded_version` 与 `DocumentIndexPublication` 那两手的存储坐标是知识目录（`DOCUMENTS_DIR`），而数据集那份字节住在 `DATA_DIR`——哪一根树 owns 这份文件＝**R687 的零拷贝问题**。本单只把行交给索引，不动目录与发布账。
2. **「第二条命」的删除生命周期**：`DELETE /api/v1/data-files/{filename}` 今天撤的是数据集那一半，知识库里的同名块**还留着**。要一格单把它接上（建议挂 R687 名下或另立 R 号，先 `rg` 取号再编号，不许凭记忆）。
3. **同一显示名撞上知识库里已有文档**：两条腿都按 display name 记账，`add_document` 的「同名换版」语义会让数据集这份表格覆盖知识库里同名文档的块。这是**未裁的口径**（要不要给数据集那一半加命名前缀属产品裁定），本单没改语义、没偷偷加前缀。
