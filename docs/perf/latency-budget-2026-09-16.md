日期：2026-09-16（测量窗口 22:28–23:15，+08:00）
测量人：W8（性能测量 worker）
基线：分支 `codex/perf-lab` @ `6c5ccd9`
被测对象：`enterprise-brain-backend-1` 容器内产品，模型 `qwen3.5:9b`（9.0B Q4_K_M，5.6 GB）

## 0. 三类数字的定义（本文所有数字都带标记，未标即错误）

- `[实测]` 我自己这次跑出来的：容器内直连 Ollama 原生 `/api/chat`（唯一能拿到
  `prompt_eval_count` / `eval_count` 的端点）或 `/v1/chat/completions`（产品真实端点，
  读 `usage`）的返回值；或后端日志里一次真实请求的毫秒时间戳差。
- `[算术]` 由 `[实测]` 数字做加减除和分段线性插值得到，不引入任何新假设。
- `[推算]` 引入了本机未验证的外部假设（公开 GPU 基准、客户库规模的分块尺寸等）。
  **`[推算]` 一律不是承诺**，采纳前必须在目标机器上重跑同一探针。

复跑命令见文末「附录 A：可复跑命令」。本文全部数字来自

## 1. 先说结论

1. **160.6 秒里约 99.5% 是模型往返，产品自己的检索/规则/落库只占 0.74 秒。**
   慢不是「检索慢」「数据库慢」，是「问了 5 次模型，而每次模型都很慢」。`[实测]`
2. **本机纯 CPU 上 15 秒不可能达到**：零上下文下，一条 230 字（≈160 token）的答案
   本身就要 24.1 秒。要压进 15 秒，答案必须短到 124 字以内且不带任何检索上下文。`[算术]`
3. `n_ctx` 实际只有 **4096**（`OLLAMA_CONTEXT_LENGTH` 未设），2944 token 的 prompt 已经
   要 94 秒，而 4402 token 直接被服务端 **HTTP 400 拒掉**。上下文天花板和超时
   天花板比想象的近得多。`[实测]`
4. `MODEL_REQUEST_TIMEOUT=60` 在 prompt ≈ **1900 token（纯 prefill）／≈1350 token
   （带 230 字答案）** 时必炸；且客户端超时**不会**取消服务端生成，2026-09-16 21:50
   那次冷启动因此连撞 5 次 60 秒、共 **302 秒**，最后返回「模型不可用」。`[实测]`
5. **每一发模型都在先生成用户永远看不见的思考 token，而产品在 `/v1` 端点上关不掉它。**
   实测生成轮 193 个 token 里可见正文只有 154 字、其余 141 字落在 `reasoning` 字段被
   产品丢弃；我试的 5 种「关思考」写法在 `/v1` 上全部无效，只有原生 `/api/chat` 的
   `think:false` 真生效。按 token 归属算，现状里约 **45–51% 的生成时间花在被丢掉的文本上**。`[实测]`
6. **那发 41.6 秒的「查询改写」经常什么都不产出。** 真实端点上它生成 300 token 全是思考、
   可见正文 0 字，于是 `json.loads("")` 抛 `Expecting value: line 1 column 1 (char 0)`
   ——这是日志那条 WARNING 的**第二个**成因（第一个是并发槽）。`[实测]`
7. **今晚只是慢，客户规模下是会直接失败。** 生成轮按 `top_k=5` 打满 500 字/块时
   prompt ≈2112 token → 单 prefill 就要 65.3 s → **必然超 60 s 超时**，用户拿到的是
   「离线模式：模型不可用」而不是一句慢答案。`[算术]`（基于 2.1 实测速率）
8. 前端**看不到流式首字**：`/ask` 的 `event: text` 只在整轮结束时发一次完整答案
   （`app/api/v1/chat.py:1134`）。所以今天「首字时间 = 总时长」，任何只砍总时长的
   改造都不会让用户更早看到一个字。`[实测]`

## 2. 第一步：复核速率曲线（`[实测]`，22:35–22:44）

方法：容器内 `python - < scripts/perf_probe_rate.py`，原生 `/api/chat`，`stream:false`，
`temperature:0`，中文语料每行带唯一编号；**每次请求前置一个随机 nonce**——Ollama 0.34
有 prompt 前缀缓存，不加盐时同一批递进语料会报出 343 t/s、72 t/s 这种不可能的速率
（我第一次跑就中招了，`docs/perf/raw/rate_prefill.jsonl` 里那条 343 t/s 就是缓存命中）。

  也就是说在本机 8 GB 内存下，把 n_ctx 翻倍对 prefill 速率影响很小（但 KV 常驻内存会涨，
  我没测内存水位，不做承诺）。`[实测]`（速率）/`[推算]`（内存风险）

### 2.3 `think` 开关：不是免费午餐，但方向要单独验

decode 300 token 时 off 36.5 s / on 42.8 s（on 慢 17%）。差别不在 prompt 侧而在输出侧——

   槽并成功**——就是那发 41.581 s 的。机制描述（并发预算=1 导致改写退回）成立，

## 4. 产品真实端点的隐藏成本：思考 token（本单最大发现）

`scripts/perf_probe_prodpath.py` 用产品一模一样的方式调 `/v1/chat/completions`
（`ChatOpenAI` + `temperature:0` + `tools`），拿到 `usage`：

```
v1_supervisor  wall 29.598s
  usage.prompt_tokens      543   cached_tokens 292   <-- [订正 R146] 原写 0，与同目录 raw/prodpath.jsonl 第 2 行不符
  usage.completion_tokens   97
  content_chars              0      <-- 用户在屏幕上看到的内容
  reasoning_chars          134      <-- 模型实际生成、被产品丢掉的内容
  finish_reason      tool_calls  tool_calls=["dispatch"]
```

**每一发模型调用都在先生成一段用户永远看不见的思考文本，然后产品把 `reasoning` 字段丢弃。**
`[实测]`

这解释了表一里两处「字太少、时间太长」的矛盾：

- ④ 生成 50.448 s 只交付 230 字：按 8.14 tok/s 反推，这发实际生成 **≈299 token**，
  而 230 字可见答案只有 ≈160 token，**约 139 token（46%）是看不见的思考**。`[算术]`
- ③ 查询改写 41.581 s 只为了一段 116 token 的 prompt 产出 3 个改写：反推生成
  **≈308 token**，而合法 JSON 输出只需 ~120。`[算术]`
- ①②⑤ 三发的 `eval_count` 96 / ~99 / 107 也全部落在「内容 0 字」上（`tool_calls`）。

粗算：现状 160.6 s 里约 **45–55 s 花在被丢弃的思考 token 上**（按每发思考占比折半估）。
`[算术]`，精确值见 `docs/perf/raw/think_off.jsonl`（第 5 节 E 档）。

### 4.1 端点级 token 归属（`usage` 不受排队影响，可直接采信）

**这条发现比"慢"更要命**：查询改写这一发在真实端点上**经常返回空正文**。

也就是说：现状链路**平均要为一发"大概率什么都不产出"的改写付 41.6 秒**。
`[实测]`（两种失败形态）+`[算术]`（41.6 s 来自日志）

（`finish=tool_calls`，两次独立重建都复现了）。今晚日志里 doc worker 只跑了 2 个往返，
说明真实那一发确实收敛了；但**"检索一轮不够就再来一轮"是这份 prompt 的常见行为**，
客户规模下（块多、相似度参差）往返数很可能 >2，表一的 5 发是**下界**而不是典型值。`[推算]`

## 5. 表二 · 四种改造的量化预期

统一口径：
- **总时长** = 从提问到 `event: text` 第一个字到达浏览器。今天 `/ask` 不流式，所以
  **总时长 == 首字时间**（`app/api/v1/chat.py:1134`）`[实测]`。

- 非模型固定开销 0.749 s 全程保留。`[实测]`

| 方案 | 今晚 1 篇 1 块：总时长 | 今晚：首字(不流式) | 今晚：首字(流式) | 客户规模 5×500 字块：总时长 | 依据 |

### 5.1 每一档砍掉了什么（对账用）

- **A = 160.552 − 27.797(①) − 15.931(⑤) − 0.033(反思)** = 116.791 s。
  三处空转里**只有 Supervisor 那两发真有收益**：
  - 「并发预算不足就不发起改写」今晚**省 0 秒**——那两发失败的改写各花 0.06 s 就退回了，
    真正贵的是**抢到槽并成功**的那一发 41.581 s（它不在这一条的射程内，属于 B）。
  - 「单任务纯问答不进反思」今晚**省 0.033 秒**——反思是纯规则。`[实测]`
  - 「已有确定性计划就不再问模型」才是硬菜：今晚 `plan=1` 且 `route_main` 本来就
    会被关键词/计划兜底覆盖（`orchestrator.py:285-305`），①⑤ 两发共 43.728 s 全可省。`[算术]`
  - 若按**字面**只省 ① 不加省 ⑤：160.552 − 27.797 − 0.033 = **132.7 s**。A 档收益区间 116.8–132.7 s。
- **B = A − 41.581(③ 多路改写)** = 75.210 s。fast 档关掉 `REWRITE_PROMPT` 后，
  检索仍走原问题 + BM25，今晚召回结果一模一样（都是同 1 个块），**零质量损失**。`[实测]`
- **C = B − ≈5 s**。上下文瘦身在今晚几乎无事可瘦：真实分块只有 116 字（≈85 token）。
  瘦身上限就是把 `DOC_PROMPT`+工具描述+记忆注入压到 250 token 以内。`[算术]`
  **C 的价值全部在客户规模**（见 5.3）。
- **D = C + GPU**，用公开基准区间：RTX 4060 8 GB 全量 offload 时 prefill 约
  700–2000 t/s、decode 约 25–35 t/s（Laptop 取 0.8×，中位 pp 800 / tg 26）。
  区间敏感性：pp500/tg20 → 17.9 s；pp1500/tg32 → 10.2 s。`[推算]`
  **两条硬警告**：(1) 9B Q4_K_M 权重 5.6 GB，8 GB 显存装完权重再放 KV + CUDA 上下文非常紧，
  一旦部分回退到 CPU，速率会掉到接近本表现值；(2) 这组数**未在本机验证**，
  客户机器实测前不得写进任何承诺。

### 5.2 反解：CPU 上要压到多少 token 才能进 15 秒？——**压不到**

用第 2.1/2.2 节实测速率（prefill 曲线插值 + decode 8.14 t/s）。结构这里取的是**比 B 档还
乐观**的下界：只算 1 次生成往返（连 doc worker 选工具那一发都省掉，即 P-1 之外再做一次
确定性检索），指令壳固定 150 token，表体是允许塞进去的检索上下文 token 数。
按真实 B 档（还要再加约 24 s 的工具往返）每一格还要再扣掉同等预算，结论只会更严。

| 目标 | 答案 120 tok(≈172字) | 答案 160 tok(≈230字) | 答案 240 tok(≈345字) |
|---|---|---|---|
| 15 s | 上下文预算 **0** | **0** | **0** |
| 20 s | 29 | 0 | 0 |
| 30 s | 374（≈1 块）| 205 | 0 |
| 45 s | 877（≈2 块）| 713 | 383（≈1 块）|
| 60 s | 1362（≈3 块）| 1212 | 886 |

（表体数字 = 允许塞进 prompt 的检索上下文 token 数；0 = 连一个分块都放不下。）`[算术]`

结论，直说：

- **零上下文、只留 150 token 指令壳时，CPU 上跑完一条 230 字答案就要 24.1 s**
  （4.4 s prefill + 19.7 s decode）。15 秒在 9B Q4 纯 CPU 上**不是调参问题，是算术问题**。`[算术]`
- 要在 CPU 上进 15 s，必须同时满足：答案 ≤ **86 token（≈124 字）**、检索上下文 **0 token**、
  并且把 doc worker 的第 1 个往返也做成确定性（否则再 +24 s）。这个产品形态企业客户不会接受。
- **CPU 现实可达区间：35–50 s**（1 个分块 + 230 字答案 ≈ 35 s；3 个分块 ≈ 45 s）。
- 因此「15 秒」只有两条路：**换硬件（D）**，或**换小模型**（本机只装了 9B 和 14B，
  14B 只会更慢；没有 3–4B 档 → 见跟进单 P-5）。`[实测]`（模型清单）

### 5.3 客户规模下会变的地方（今晚结论不能直接搬）

今晚知识库 = **1 篇 1 块 116 字**，所以：检索 0.242 s、生成轮 prompt 仅 472 token。
客户真实库（几千篇）会变的是**上下文尺寸**，不是速率：

| 项 | 今晚 `[实测]` | 客户规模 `[推算]` | 影响 |
|---|---|---|---|
| `top_k=5` 命中块数 | 1（库里只有 1 块）| 5（打满）| 生成轮 prompt 472 → **2112 token** |
| 生成轮 prefill | 13.7 s | **65.3 s** | **> 60 s 超时 → 直接返回离线文案** |
| BM25 索引 | 1 篇，构建 0.4 s | 数千篇，全量 `collection.get()` 重建 | 见 `retrieval_pipeline.py:102` 的 `build_index`，索引重建是全局锁 |
| 重排 | **未生效**（日志：本地找不到 `BAAI/bge-reranker-base`，回退 RRF）| 若客户放了模型 → 每查询 5×6 pair 打分 | 今晚检索成本被**低估** |
| 多路召回 | 6 路查询命中同一块 | 6 路各命中不同块 | 改写才第一次有意义 |
| 子图 checkpoint | 会话首轮，worker 历史很短 | `{thread}:{worker}` 逐轮累积（`orchestrator.py:349`）| **多轮对话必然把 prompt 推过 4096 → HTTP 400** |

**最重要的一条**：客户规模下「生成」这一发会因为 prefill 涨到 65 s 而**撞上
`MODEL_REQUEST_TIMEOUT=60`，用户拿到的不是慢答案，而是「离线模式：模型不可用」**。
`[算术]`（基于 2.1 实测速率）+`[实测]`（超时默认值与兜底文案在 `model_handler.py:50/112`）。
也就是说：**今晚只是慢，客户上线后是会直接失败。** 这是 C 档（上下文瘦身）的真实必要性，
而不是"快一点"的锦上添花。
### 5.4 E 档（本单新发现）：关思考——**在产品的端点上关不掉**

我按 4 种公开写法 + 1 种兜底，在产品真实端点 `/v1/chat/completions` 上对**同一条
生成轮消息体**各跑一次（`docs/perf/raw/think_off.jsonl`）：

| 写法 | 可见 content 字 | reasoning 字 | 生成 token | 端到端 wall |
|---|---|---|---|---|
| 现状（不带任何参数）| 127 | 108 | 147 | 52.5 s |
| 顶层 `"think": false` | 119 | **123** | 153 | 49.7 s |
| `"thinking": {"type":"disabled"}` | 122 | **108** | 146 | 51.1 s |
| `"options": {"think": false}` | 123 | **108** | 146 | 62.4 s |
| `"chat_template_kwargs": {"enable_thinking": false}` | 123 | **106** | 145 | 51.6 s |

`[实测]`（wall 含排队，前 5 行都受我在 23:01 制造的幽灵请求影响，**只有 token 归属可采信**；
无干扰的复样本 `repeat0` = **30.593 s / 193 token / content 154 字 / reasoning 141 字**）

**结论：5 种写法全部无效，`reasoning` 始终存在。** Ollama 0.34.0 的 OpenAI 兼容层

off 时 `thinking` 为 0 字、on 时可见正文为 0 字）。`[实测]`

所以 E 档不是"加一个请求参数"，而是**把模型调用从 `/v1` 迁到原生 `/api/chat`**

- 生成轮 thinking 占比实测 **≈45–51%**（141/193、108/147 token 两组）`[实测]`
- 若能关掉：生成轮 30.6 s → ≈19 s；按表一的比例外推到全链路（5 发都要交这份税），

- 代价：迁端点要重做工具调用的报文适配（`/v1` 的 `tool_calls` 结构与原生不同），

  ——这也是我在 7.1 里把 E 列为"必做但必须先建基线"的原因。

修正 7.1 的第 5 条排序：**E 的收益大于 C，但它需要质量基线当前置条件，所以排第 5 是对的，
不能当"快赢"卖。**

## 6. 表三 · 超时与并发策略

### 6.1 `MODEL_REQUEST_TIMEOUT=60` 在多长上下文下必炸

前提：`MODEL_REQUEST_TIMEOUT` 在容器里**没有设置**，取代码默认 60 s
（`app/common/model_handler.py:50`；容器 env 实测 `<unset>`，`[实测]`）。
超时是**整发调用**（prefill + 全部生成）的预算，所以答案越长阈值越低：

| 该发要生成的 token | ≈可见内容 | prompt 硬顶（超过即 100% 超时）|
|---|---|---|
| 0（纯 prefill / 单 token）| — | **1948 token** |
| 120 | 一段短 JSON | **1497 token** |
| 160 | ≈230 字答案 | **1347 token** |
| 240 | ≈345 字答案 | **1034 token** |
| 400 | ≈570 字答案 | **375 token** |

`[算术]`，由 2.1 实测 prefill 曲线反插值 + 8.14 t/s decode 得出。

**产品现状离这条线有多近**：今晚生成轮 prompt 472 token（安全），但客户规模 2112 token
→ 该发需要 ≈100.7 s → **必然超时**。`[算术]`

已经付过的学费（`[实测]`，同日 21:50 那次冷启动）：
`[Plan] 21:50:11,311` 之后连续 **5 次** `Request timed out`（21:51:11 / 21:52:11 /
21:53:12 / 21:54:12 / 21:55:12，每次都精确 60.0–60.3 s），整轮 **302 秒**，
最后 `[doc] 完成 status=model_unavailable 结果 144 字` —— 用户等了 5 分钟拿到一句兜底文案。

**机制：我先前推测的「超时留下幽灵任务」被我自己的受控实验否掉了，这里点名订正。**

- 受控实验（`queue.jsonl` `ghost_*`）：发一发 400 token 的生成，8 秒后干净关闭 socket，
  紧接着连发 3 小请求 → 分别 **1.228 / 0.950 / 0.915 s** 正常返回。
  **Ollama 0.34.0 在客户端断开后确实会停止生成**，没有排队幽灵。`[实测]`
- 那 182.730 s 的真因是另一回事：我用 `taskkill /T` 杀的是**宿主侧 `docker exec` 客户端**，
  容器内那个 python 进程并不随之退出，它继续把请求占住。所以"杀客户端 ≠ 取消容器内工作"
  是**探针/运维坑**，不是模型服务行为。受影响的那一行已作废，改用 22:57 那次干净的
  29.598 s。`[实测]`
- 因此 21:50 那 302 s 的正确解释是朴素的那种：**5 发各自都真的超过 60 s**
  （冷加载 6.9 s 在前，逐发上下文还在长大），每发撞自己的 60 s 墙，
  产品把 5 发**依次**跑完，于是 5×60 = 302 s。超时在这里的作用不是放大，
  而是**让一轮注定失败的请求再多烧 4 分钟**。`[实测]`（时间戳等间隔 60.0–60.3 s）

建议值与理由：

1. **`MODEL_REQUEST_TIMEOUT` 从 60 s 提到 120 s 不够，方向错了。** 正确做法是
   **给 prompt 设预算而不是给时间设预算**：把每一发的 prompt 硬上限锁在
   **1200 token**（对应 230 字答案时留 40% 余量），超时保持 60 s。
   这样最坏情况是"答案短一点"，而不是"整轮报废"。`[算术]`
2. **超时要「中止整轮」而不是「中止这一发」**：既然已实测确认 Ollama 会随客户端断开停止生成，
   产品就不该在第 1 发超时后继续发起剩下 4 发。判据：任一 model_unavailable 之后整轮立即
   收口并给出明确错误，不再产生新的模型调用——否则一次冷启动就是 302 s。[算术]
3. 冷启动单独处理：`load_duration` 6.9 s + 首发热身，让**第一条真实请求不付费**
   ——服务启动后主动发一发 1-token 预热并把 `keep_alive` 设长。这是纯收益，
   今晚的 302 s 事故一半来自冷启动。`[实测]`（load 6.883 s）
4. `MODEL_CONCURRENCY_WAIT_SECONDS` 未设置 → 默认 60 s（`model_budget.py:66`），
   而 `ModelHandler.chat` 走的是 `wait_seconds=0`（`model_handler.py:97`）——
   **同一个进程里两种等待语义**：LangChain 路径排队 60 s，改写路径 0 s 直接放弃。
   今晚改写退回就是这条造成的。建议统一为"排队"，并把预算从 1 提到 2（见 6.2 依据）。`[实测]`（代码与 env）

### 6.2 `MODEL_MAX_CONCURRENCY=1` 下多人同时问

先讲清机制，再给数：并发槽只有 1，且 LangChain 路径最多等 60 s
（`MODEL_CONCURRENCY_WAIT_SECONDS` 默认）就**放弃并返回离线文案**——所以多人场景
不是"排队等久一点"，而是**第 2 个人之后直接拿到「模型不可用」**。`[实测]`（代码 + 日志
`budget exhausted` ×2）

队尾等待 = (N−1) × 单请求总时长。这条我先算后测，实测**成立**（`docs/perf/raw/queue.jsonl`：同一时刻并发 N 发 200 token 请求，Ollama 单实例严格 FCFS 串行，**每发自己的 decode 不被稀释**（单发 27.3 s，并发下仍是 23.2–28.3 s），代价全部落在等待上：N=2 两发完成于 28.5 s / **58.0 s**；N=5 最慢一发 **127.8 s** ≈ 5 × 25.6 s。`[实测]`）：

| 方案 | 单请求 | N=2 | N=3 | N=5 | 2/3/5 人实际结果 |
|---|---|---|---|---|---|
| 现状 160.6 s | 160.6 | 160.6 s | 321.2 s | 642.4 s | **全部 >60 s → 第 2 人起离线文案** |
| A 116.8 s | 116.8 | 116.8 s | 233.6 s | 467.2 s | 同上 |
| B 75.2 s | 75.2 | 75.2 s | 150.4 s | 300.8 s | 同上（75 > 60）|
| C 70.2 s | 70.2 | 70.2 s | 140.4 s | 280.8 s | 同上 |
| **D 13.3 s** | 13.3 | 13.3 s | 26.6 s | 53.2 s | **2/3/5 人都能在 60 s 内排到** ✅ |

这张表是本单最该被产品看见的一张：**A/B/C 都没有解决"多员工同时用"，一个都没有。**
75 s 和 160 s 对第 2 个员工是同一件事——都是拿不到答案。并发能力不是调出来的，
是**把单请求耗时压进 60/N 秒**换来的。按这个判据：

- 要支持 **2 人**同时用：单请求 ≤ 60 s → 需要 B/C + 客户规模下的瘦身（70 s 还差一点），
  实际要把等待预算 `MODEL_CONCURRENCY_WAIT_SECONDS` 提到 ≥90 s，或压到 ≤60 s。
- 要支持 **5 人**同时用：单请求 ≤ 12 s → **只有 D（GPU）**，或 D + 关思考。
- 或者把 `MODEL_MAX_CONCURRENCY` 从 1 提到 2：但这在 8 GB / 纯 CPU 上会把两个请求
  各拖慢约一倍（同一个 CPU 分摊），**总吞吐不变**，只是把"直接失败"变成"两个都慢"。
  这条我没实测（需要真实双请求 + 产品链路），标 `[推算]`，且明确不建议单独采用。
## 7. 「这个速度谁还用」——我的回答

先把最难听的话说清楚：**今晚这套链路（现状）不具备给任何真实企业用户使用的资格。**
不是"体验差"，是三条同时不成立：160 s 一轮、第 2 个人并发直接拿离线文案、
客户库规模下会超时失败。`[实测]`

但"慢"在这里不是模型不行，是**同一个模型被问了 5 次，其中 2 次是纯空转、
1 次在今晚毫无价值，而每一次都在先生成用户看不见的思考文本**。这是好消息——
结构问题比硬件问题便宜。

### 7.1 我认为可上线的最小改造组合

**必做（按性价比排序，前 3 条不改模型、不改硬件）**

1. **确定性计划命中时彻底跳过 Supervisor（含第 2 发）** → 省 43.7 s。
   今晚 `build_task_plan` 已经给出 `tasks=1`，`route_main` 又一定会用计划/关键词
   覆盖模型决策，模型这两发**没有一次真正影响过路由**。这是纯白送。`[实测]`
2. **fast 档默认关闭多路改写与子问题拆分** → 省 41.6 s。
   今晚 6 路召回命中同一个块，改写产出对答案零贡献。`[实测]`
   注意：这一条在客户规模下**不再是零损失**（见 7.2），所以要按库规模分档，不是一刀切。
3. **生成轮按 token 流式透传，让 `event: text` 提前** → 总时长不变，但**首字从 160 s
   降到 ≈148 s；叠加 1+2 后首字 ≈ 38.5 s**。今天用户是"整轮结束才看见第一个字"，
   这是纯粹的产品自伤，改 SSE 一处即可。`[实测]`（现状不流式）+`[算术]`（改后首字）

做完 1+2+3：**总时长 75 s、首字 ≈53 s**。仍然不快，但已经"看得见有人在干活"。

4. **上下文预算硬上限 1200 token/发**（第 6.1 节判据）。这条不是为了快，
   **是为了客户上线后不返回「模型不可用」**。必做。
5. **关掉被丢弃的思考 token**（若 `think:false` 在 `/v1` 上可用，见 E 档实测）。
   预期再省 30–45% 的生成时间，改动量是一个请求参数。

**可缓**

- C 档的"把 `DOC_PROMPT`/工具描述/记忆注入压到 250 token"：今晚只值 5 s，
  等客户库上线后按第 5.3 节重新定价。
- 上下文向量化裁剪、RRF 早停、检索缓存等：在 prefill 只占 0.5% 的今晚没有意义。
- `MODEL_MAX_CONCURRENCY` 调整：先解决单请求耗时，再谈并发，顺序反了只会更糟。

**硬件决策线（用数字划，不用感觉划）**

- 客户 SLA 只要「2 人能用、60 s 内出答案」→ **软件改造 1+2+4+5 可能够**，先别买卡。
- 客户要「5 人同时问、15 s 内」→ **必须 D（GPU）+ 流式**。按 6.2 的表，
  纯 CPU 下 5 人 = 队尾 280 s，任何软件优化都救不回来。
- 买卡前先确认一件事：**这台 Docker VM 现在只有 8 GB 内存、`size_vram=0`、
  `.wslconfig` 写死**。W8 无法验宿主的 RTX 4060 能否透传进容器（属于运维/授权范围，
  不在本单红线内），但**这是 D 档的前置条件**，不通就一切都无从谈起。`[实测]`（size_vram=0）

### 7.2 fast / thorough 该按什么条件选（区分今晚结论与客户规模）

今晚的测试库是 **1 篇 / 1 块 / 116 字**。在这个尺寸上"关改写"是纯赚，
**但这不是通用结论**。给一条可判据的选择规则，按成本而不是按口味：

| 判据 | fast 档 | thorough 档 |
|---|---|---|
| 可检索分块数 | < ~200 块 | ≥ ~200 块 |
| 单查询能否命中 top_k 上限 | 否（库太小，改写无候选空间）| 是 |
| 生成轮 prompt 估算 | ≤ 600 token | 600–1200 token（超 1200 必须先裁剪再谈改写）|
| 提问类型 | 制度条款、单点事实（"回款周期多少天"）| 跨文档汇总、对比、"有哪些/全部/差异"|
| 并发人数（同机）| ≥2 人 → 强制 fast | 仅 1 人才允许 thorough |
| 首次命中是否为空 | 空 → 允许升级到 thorough 重检一次 | — |

**今晚结论**：fast 档对答案质量零损失（同 1 个块），且省 41.6 s。`[实测]`
**客户规模下会变**：分块上万时改写确实能拉开召回差异（不同路命中不同块），
但那时**每一发的 prefill 成本也会同步上涨**，thorough 的代价从"41 s"变成
"41 s + 生成轮超时"。所以真正的产品判断是：

> **thorough 档在纯 CPU 单机上不可交付。**它只在 D（GPU）之后才成为一个可以开放给用户
> 的选项；在 CPU 客户机上，fast 不是"降级档"，而是**唯一档**。`[算术]`

还有一点必须提醒：会话问答**故意绕过了答案缓存**
（`use_answer_cache = not bool(request.session_id)`，`chat.py:936`），所以"第二个员工
问同一个问题"不会秒回。企业场景里重复问题是高频事件，这是一个未使用的免费加速位
（带权限作用域，缓存键已含 `answer_scope`）。`[实测]`（代码）

## 8. 建议新立跟进单（本单不改代码，只出草案）

判据统一为：**必须能用本文探针复跑并给出数字**，不接受"感觉变快了"。

### P-1 · 确定性计划命中时不再调用 Supervisor（含第 2 发）
- 判据：同类问题的模型往返次数 5 → 3；端到端 160.6 s → **≤120 s**（用
  `scripts/perf_probe_rounds.py` + `[ASK]` 日志双验）。
- 改动面：`app/agents/orchestrator.py:154` `main_agent_node`（计划命中时短路）、
  图路由 `:666` 附近。
- 风险：Supervisor 在"计划判错 worker"时是唯一纠正面；`route_main:285-305` 已经证明
  计划/关键词实际会覆盖模型，需要保留一条"计划为空才问模型"的回退，并加测试覆盖
  `plan=[]` 的复合问题。

### P-2 · 多路查询改写改为条件触发 + fast/thorough 分档
- 判据：fast 档端到端 ≤ **80 s**；thorough 档仅在分块数超阈值时可用。
- 改动面：`app/rag/retrieval_pipeline.py:36-63,270-275`（无条件 `rewrite` → 按库规模/
  提问类型/并发余量决定）。
- 风险：**当前无任何质量评测基线**，一旦关掉改写就没有对照数据证明质量没掉。
  要求先落一组 20 题离线对照（可复用 `scripts/run_quality_evaluation.py` 的形态，
  不改它），再启用分档。私有化客户的库分布未知，硬编码阈值要可配。

### P-3 · `/ask` 生成轮按 token 流式透传
- 判据：`event: text` 首次携带内容的时间 ≤ 总时长的 50%；探针
  `v1_doc_react_2_stream` 的 `first_content_s` 为参考实现值。
- 改动面：`app/api/v1/chat.py:1134` 附近的收口逻辑；`docs/api/contract-v1.md:604-611`
  的 SSE 契约（涉及前端，须与前端 owner 协同，**W8 无权改 `frontend/`**）。
- 风险：契约文档明确写了 legacy 频道"删掉即视为 breaking change"（freeze rule 1），
  必须增量加 `result.partial` 而不是原地改 `text` 语义；前端解析器是 F2 的阻塞项。

### P-4 · 超时策略与取消语义
- 判据：任一发 prompt > 1200 token 时**不发出去**（裁剪后重发）；冷启动首问
  不再出现 5×60 s 级联；`[ASK]` 窗口内不再出现 `status=model_unavailable`。
- 改动面：`app/common/model_handler.py:50,97,112`、`app/common/model_budget.py:53,66`、
  部署默认值（`deploy/**` 不在本单范围，需总控确认 env 落点）。
- 风险：把 timeout 调大只是把失败推迟。实测 Ollama 会随客户端断开**停止生成**（`queue.jsonl` 的 ghost 组），所以真正要改的是「一发超时后仍继续发起下一发」这个循环本身。另注：`docker exec` 客户端退出 ≠ 容器内进程退出，运维收口要按容器内 PID。

### P-5 · 关闭被丢弃的思考 token / 引入小模型档位
- 判据：`/v1` 响应的 `reasoning_chars == 0`（或产品显式渲染思考），且端到端
  生成轮 ≤ 现状 65%。**二选一，不许默默丢字。**
- 改动面：`app/agents/nodes.py:256`（`ChatOpenAI` 加请求参数）、
  `app/common/model_handler.py:104`。
- 风险：关掉思考可能降低复杂制度题的准确率——**这条必须先做质量对照**（与 P-2 同一
  套 20 题基线）。换 3–4B 小模型是同一判据下的另一条路，本机目前只装了
  `qwen3.5:9b` / `qwen2.5:14b` / `nomic-embed-text`，无小模型可选。`[实测]`

### P-6 · 子图 checkpoint 会让多轮对话撞 4096 硬顶
- 判据：同一会话连续 5 轮提问，最大 `prompt_eval_count` < 3600（留 12% 余量）；
  不再出现 `exceed_context_size_error`。
- 背景：`context_length` 实测 **4096**（`OLLAMA_CONTEXT_LENGTH` 未设），4402 token
  直接 **HTTP 400**；而 doc worker 子图按 `{thread}:{worker}` 累积历史
  （`orchestrator.py:349`），`compress_messages` 阈值是 **20 条**
  （`app/memory/summarizer.py:10`）——**在 4096 的天花板下，20 条才压缩太晚了**。
- 改动面：`compress_messages` 阈值改为按 token 而非条数；或给 `OLLAMA_CONTEXT_LENGTH`
  一个显式值并配套内存评估（实测 8192 n_ctx 只让 prefill 慢 3.3%）。
- 风险：压缩本身要调模型（又多一发）；提高 n_ctx 会涨 KV 常驻内存，本机 8 GB 需实测。
