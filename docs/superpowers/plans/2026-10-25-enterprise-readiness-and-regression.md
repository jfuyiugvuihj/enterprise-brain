# 企业使用体验完善与历史测试收尾计划

> 2026-10-25 评审稿。本文是实施与验收安排，本轮只编制计划，不启动开发、模型、测试、数据库操作或部署。
> 执行者按 writing-plans / executing-plans 的分任务方式落实；任务状态仍只更新 docs/backlog.md。本文不另建完成度账本，不把建议能力写成已经获得实施授权。

**目标**：让企业员工能独立完成资料查询、经营分析和异常核查，取得可信成果；收尾既有测试问题，证明指定环境可供试用和交付。

**架构**：复用现有资料登记、版本、任务、计算记录、成果、确认、权限及审计。保留私有化部署、本地模型优先和 PGVector；改进用户流程与现役实现，不另建平行系统。

**技术范围**：FastAPI、现有 Agent/任务处理、PostgreSQL + PGVector、Redis、Vue、现有图表/PDF生成与 Docker Compose。

## 1. 当前约束与执行边界

1. 本地 GPU 正被训练占用。训练完成时间未知，因此本计划采用“条件满足后开始”，不写假定的启动日期。
2. 当前只做读日志、读代码、方案与材料整理。训练期间不运行 Ollama 请求、嵌入/OCR、压测、全仓 pytest、镜像构建或容器重建；也不把负载挪到 CPU 上抢内存、磁盘和 CPU。
3. 后续如获准先实施低负载代码改动，可以离线编辑；是否运行轻量检查仍先确认资源条件。代码写完、轻量检查通过均不能宣称业务功能完成。
4. 真实端到端验收必须等待明确的空闲窗口，使用指定版本、真容器、现役 PG/Redis、本地模型和浏览器；后端变更先完成镜像与运行源码一致性检查。
5. 保留当前资料与其他 Agent 的修改。不开新长回归、不清理未知工作树、不批量改文件密级、不顺带 push，不改变训练进程或其服务配置。
6. 新功能限于本文评审通过的批次。数据更新、常用分析、密码重置和账号停用涉及新行为，必须在实施前确认本计划中的默认业务规则。
7. 操作手册继续从用户角度写，并区分手机与电脑入口。新手册目前在本地预览中，主站上线与部署复验单独安排。
8. 不扩建通用 OA、付款、自由权限设计器、独立手机 App、自动经营决策或通用多表联查，不启远程模型回退。

### B2. 多问题与任务意图

用户任务：一次提两三个问题，系统逐项回答；条件不同不串数，有一项不能做时其余项仍有明确结果。

现状：app/agents/task_review.py::independent_period_questions 已有特定编号、多期间问题拆分，并非任意多问题的通用保证。本轮不能仅因函数存在而认定全部支持。

| 输入场景 | 要检查的行为 |
| --- | --- |
| 一问，单期间单指标 | 不为了流程完整而重复计算或额外生成报告 |
| 两问，两个期间各算合计 | 两组条件和结果独立，顺序与问题一致 |
| 三问：合计、主要贡献、制度要求 | 计算与引用分别可查，贡献不写成确定原因 |
| 五问，包含缺少字段的一问 | 每项有结果或明确无法回答的原因；不漏题、不编数 |
| 没编号的连续提问 | 识别不可靠时明确列出待处理问题供确认，不静默只答最后一问 |
| 同一话题连续追问 | 修改条件只作用于指定问题，历史结果与原范围保留 |
| 多个问题要求报告 | 先明确合成一份还是分别生成；防止重复登记或遗漏子题 |
| 一项无权或缺资料 | 不因其他项可用而放行受限项，也不把缺数据当零 |

## 6. C批：补齐企业使用的必需缺口

### C1. 管理员帮助员工恢复账号

建议默认规则：保留用户输入旧密码自行改密；增加管理员重置为新临时密码的受控动作，首次登录后要求改密。临时密码通过企业现有认可方式交付，本轮不接邮件/短信。

步骤与边界：

- [ ] 核对 app/api/v1/auth.py、app/common/auth.py 与现有用户存储/认证检查，优先利用现有角色、密码哈希及审计。
- [ ] 管理员选择目标账号，页面明确“重置后原登录失效”，确认后执行；不得要求管理员知道旧密码。
- [ ] 重置后撤销该账号既有会话/令牌效力。授权续跑重新读取当前账号状态，不能只用旧JWT。
- [ ] 记录谁重置了谁、结果与时间；密码不进入审计、日志、文档、URL或Trace。
- [ ] 忘记密码页与管理员操作说明对应，失败可重试且不显示虚假成功。

验收：普通员工不能重置他人；管理员可完成重置；旧密码和旧令牌不能继续访问；新临时密码可登录并按规则更改；其他账号不受影响。写集预计为认证/API、用户存储迁移（确需时）、AdminPanel.vue、登录/改密页面与权限测试。

### C2. 账号停用与恢复

建议默认规则：停用立即禁止登录和后续受保护访问；保留资料、任务、成果与审计。恢复访问后继续按当前部门和角色授权，不自动恢复已取消的任务。

- [ ] 先确认现有存储是否已有状态字段，复用而非重复加字段。
- [ ] 增加停用/恢复入口，展示目标账号和影响，防止误操作最后一个可用管理员。
- [ ] 待执行/待确认任务在执行前校验账号状态；运行中的任务在现有可中断节点停止后续动作，不能承诺撤回已经发生的操作。
- [ ] 已产生文件保留，但停用账号不能继续读取或下载；管理员按现有权限管理这些资源。

验收：停用、恢复、旧JWT、旧下载链接、排队任务、待确认任务分别有结果；历史审计不被删除。本功能不能以“删除后再开一个同名账号”代替。

### C3. 让业务人员看懂并相信分析范围

用户任务：发送前知道选了什么，回答后知道实际用了什么，报告中看到同一套依据。

- [ ] 把“下次准备使用的资料”和“这次实际使用的资料”明确区分，保留已有 AnalysisContext 信息。
- [ ] 从 CalculationStorage、任务上下文和现有成果登记读取文件版本、期间、筛选、单位、记录范围；多问题按子问题分别呈现。
- [ ] ChatPanel 的 contextScope 文本提取仅用于旧记录回看，明确标注不能确认的旧信息；新任务不以模型措辞作为唯一记录源。
- [ ] 用户修改统计条件后生成新轮次结果，报告复用该轮实际记录；缺少条件先询问，不静默补猜。
- [ ] 首页/资料页提供少量任务引导，按已有字段提示可做的分析；没有日期列时不诱导用户点趋势分析。

验收：同一结果在聊天、范围卡、报告与返回历史任务中一致；刷新、更换资料、资料更新、缺失字段与多问题场景不会串范围。写集：ChatPanel.vue、AnalysisContext.vue、DataPanel.vue、现有模板、CalculationStorage与API的必要契约扩展。

## 7. D批：把周期性工作做得可重复

### D1. 显式更新经营资料

建议默认规则：普通上传同名仍拒绝；用户必须从有更新权限的资料进入“上传新版本”，确认目标资料与新文件后新增版本。新文件登记成功前，旧版本继续可用。

- [ ] 复用 DatasetRegistry::register、versions、get_version 与现有版本文件路径；先核对其已有更新契约。
- [ ] 检查目标所有权、部门、密级和当前操作权限；更新不能扩大共享范围或绕过行权限。
- [ ] 新版本保留独立文件与哈希；登记/索引失败时展示失败并保持旧活动版本，避免文件和目录各说各话。
- [ ] 标明新旧版本、更新时间和字段变化；仅在有实际计算依据时展示行数变化等摘要。
- [ ] 旧会话、计算和报告继续指向原版本；新分析由用户明确选择新版。
- [ ] 明确已有告警的版本策略：建议固定版本规则继续固定；需要跟随更新的规则显式设定，经重新校验后使用新版本，每次巡检保留实际版本。

验收：正常更新、重复内容、同名不同资料、字段缺失、跨部门更新、失败回退、旧报告回查与告警重算分别有确定结果。禁止直接覆盖旧路径。路径：app/api/v1/data.py、app/storage/datasets.py、DataPanel.vue、task_review.py；复用 test_r249_dataset_version_chain.py、test_r256_dataset_version_scope.py。

建议先提供“按这次条件再分析”的轻量入口，验证重复需求后再做命名保存。第一版归当前用户，不开放团队共享与自动定时执行。

- [ ] 保存用户问题、结构化期间/筛选/指标、资料引用与必要设置，不保存旧授权、不把旧答案当新结果。
- [ ] 下一次选择新版本后先检查字段、单位及权限；字段改名或缺失时让用户修正，不能直接猜列。

- [ ] 每次执行生成独立任务/计算/成果，能回查本次输入；不修改旧报告。

验收：同一分析应用于新资料得出新数字；无权、缺字段、单位改变时不会沿用错误条件；取消后没有多余报告。优先复用 task_context 与会话存储；确需持久化配置时只增加最小记录，不新建报表平台。

## 8. E批：GPU释放后的复验与主站部署

### E1. 开窗前准备

- [ ] 由用户明确训练已完成/可使用资源，不因检测到GPU短暂空闲就启动。
- [ ] 指定主站或隔离环境、代码与镜像版本、测试账号和资料、回滚方式；确认训练相关进程不在变更目标内。
- [ ] 数据库/文件备份先验证路径与可读性；故障注入使用隔离实例，不能停生产PG/Ollama冒充普通验收。
- [ ] 用指定解释器和现有脚本，核对预估与运行范围后再启动。小修同名验证预算≤5分钟；若过大应切分写集，而非把所有用例强制超时。

### E2. 顺序与最小覆盖

1. **定点复验**：先解决A批具名失败，每组结束立即保存结果。无模型的适用项仍需真实隔离PG/Redis验证核心接口。
2. **三个业务任务**：员工制度查询；负责人单经营表+制度核查并报告；管理人员告警→分析→处理→成果。复用已有材料和独立答案，不为出图扩造数据。
3. **多问题复验**：按B2矩阵选择代表输入，逐题核算，检验答案、图表和报告覆盖一致。
4. **跨账号与状态**：针对本批涉及的账号恢复/停用、版本、下载、确认续跑补负向场景。
5. **排队容量**：先做单会话基线，再2个独立会话，再在资源允许且目标用户数已明确时增加；记录首个反馈、排队时长、总耗时、成功/失败、资源占用。没有足够样本不报告P95。
6. **浏览器**：电脑1440×900；手机代表宽度320/377或390、768；真荣耀/微信重验变更路径与实际保存。新浏览器仅在有设备时测试。
7. **新版主站**：帮助入口、目录、资料名称、手机导航与当前部署一致；检查页面不是旧缓存资源。后端变更按项目规则重建并验证回滚，前端单独变更不重建模型服务。

验收四项分别写通过/不通过/未验：链路、数据、内容、呈现。不适用须有理由。HTTP200、文件存在或测试退出0只能证明对应环节，不能代替完整质量检查。

### E3. 全仓回归的位置

全仓回归安排在具名产品失败处理后、机器空闲时。上次120分钟未结束，因此当前没有可靠总时长，不能承诺“只剩几分钟”。它不替代业务验收，也不应阻挡与失败无关的小批交付。

需要启动时，先说明估时未知和既往耗时，再由单次本地脚本管理；不会为得到完整汇总反复自动重启。全仓红仍须归因；用户关键链路失败阻塞交付，纯历史检查保留说明，不能悄悄忽略。

执行前先检查用例的环境、连接目标与隔离目录；以下不是允许立即运行的一键清单。每次只取对应修复的小集合，不同时启动全部命令。

## 9. F批：真人试用、新机与恢复

### F1. 小范围真人试用

建议邀请一名员工、一名业务负责人和一名管理人员，使用企业批准的真实资料完成上述三类任务。可由同一人先覆盖多种任务，但记录实际人数，不把模拟账号算真人。

第一次观察不口头教按钮，只提供正常手册。记录任务是否独立完成、耗时、求助次数、错选资料、返工、结果是否被采用；与该人员原有人工方法对比，不预设节省比例。

建议先观察3—5个工作日作为首轮反馈窗口，这只是试用安排，不是已证明效果。每天优先修阻塞和严重误导；反复出现的重复工作再推动D批，零散偏好先归类。无权限泄露/错数等严重问题，且三类任务能完成并获得业务人员认可，才进入更大范围试用。

### F2. 新机器与局域网

VMware Linux虚拟机可以用于全新安装验收，前提是指定干净环境、资源和网络就绪。它能证明安装流程及虚拟环境访问，不能替代所有客户硬件或真实独立电脑的兼容性结论。

- [ ] 按 deploy/README.server.md 从干净系统安装，核对依赖、配置、PG初始化、账号与模型准备；记录需要手工救场的步骤并修说明。
- [ ] 主机、手机和另一设备分别访问企业入口；虚拟机测试注明宿主机、网络模式和实际访问方向。
- [ ] 正式交付明确内网地址/域名、HTTPS信任、休眠策略和必要端口；不关闭防火墙或新增公网穿透。

### F3. 备份恢复和72小时运行

复用 backup_workspace.py、backup_database.py、restore_workspace.py、restore_database.py，先审阅参数，再在隔离目标执行。恢复内容包括PG及权限、原文件、会话、计算记录、图表/PDF与部署配置；密码/密钥按企业规则保管。

恢复后核对授权访问、原文件哈希、旧会话、成果下载与版本关系；旧队列不重复执行已完成动作，不覆盖源环境。不将同机器重建称为灾备恢复。

安装和恢复通过后开展72小时观察：按既定任务节奏验证可用性、任务失败、资源趋势和文件持久性。交由本地持久化脚本记录，不依赖主Agent常驻或长期心跳；观察通过只代表该版本、硬件和负载，不能外推更大容量。

## 11. 工作量、估时与角色安排

以下是规划量级，不是完工承诺。复杂度取决于旧失败实际归因、现有用户存储/令牌机制、资料规模和测试窗口；完成A批后重新估算，避免凭用例百分比报剩余时间。

| 工作包 | 初步工作量 | 主要不确定项 |
| --- | --- | --- |
| A：基线、失败归类与范围确定 | 0.5—1个工程工作日 | 旧日志缺少完整nodeid，需要多少补证 |
| B：具名旧问题定点修复 | 1—3个工程工作日，其他失败发现后另估 | 真产品缺陷数量，而非F/E数量 |
| C1/C2：重置与停用 | 1—3个工程工作日 | 是否已有状态/令牌撤销机制与迁移需要 |
| C3：范围展示和新手流程 | 1—2个工程工作日 | 已有结构化字段能否直接供前端消费 |
| D1/D2：版本更新与重复分析 | 2—4个工程工作日 | 文件/目录/索引一致性、告警版本策略 |
| E：定点与业务/部署复验 | 1—2个工程工作日的准备和处理量；运行窗口另计 | 模型速度、内容返工；不含全仓未知长尾 |
| F：试用和交付 | 试用建议3—5工作日；安装恢复另估；观察满72小时 | 人员、设备与企业环境 |

工程工作日只是工作量单位，不等同于Agent自然日，也不靠增加并发压缩模型运行时间。这些区间不能直接累加成确定交付日期；资源窗口与业务材料是外部依赖。

Luna处理机械性只读盘点、日志提取、已定文案整理；主控负责根因判断、权限/版本契约、体验取舍和最终验收。可并行的实施必须写集不重叠、独立工作树；主树与在跑测量窗口禁止交叉改写。只有独立任务足够时才开并行席位，不为凑人数制造文档。

## 12. 批次出口与待确认业务选择

每批交付包含：用户能完成的动作、实际修改、验收四项结果、日志/截图/文件位置、未覆盖范围和下一批依赖。失败保留原始日志，修复后只先重验受影响行为；不能用长篇总结代替可演示结果。

实施前需要确认的建议规则如下，本轮不要求立刻回答：

1. 账号恢复采用“管理员临时密码＋首次改密＋旧登录失效”；停用保留历史，恢复不自动续跑旧任务。
2. 经营资料更新必须显式创建新版本；旧成果不换版。告警默认固定版本，需要跟随新版时显式设置。
3. 常用分析先做本人复用，不做团队共享、定时执行或隐式改变期间。
4. 目标试用部门、真实任务和获准资料由业务方指定；目标同时使用人数与可接受等待时间先约定，再测量。
5. 新机验收可采用指定的干净VMware Linux虚拟机；真实独立设备和生产硬件另按交付范围说明。

本轮完成标准是“这份计划覆盖企业使用缺口和历史测试债务，实施者能按批次执行”。产品完成标准仍是真环境中任务可演示、数据与内容可信、呈现可用。两者不得混写。
